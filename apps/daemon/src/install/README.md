# External binaries the Daemon installs

Each tool here follows the managed model server's pattern (`prediction/managed`, ADR 0049): a pin file with the upstream release, its commit and every platform's asset (URL, size, SHA-256 from the release's own digests), and `downloadFile` to fetch it size-bounded into `.part`, check the hash and rename it into place. It lives under `~/.polaris/tools/<tool>/<version>/`; a new pin installs beside the old version, then deletes it.

Nothing installs at start or on a timer. `onDemand.ts` holds the shared lifecycle: the first caller that finds the tool missing starts it in the background (`current` goes on without it; `ensure` waits), and later callers share that one install. Each attempt is cancelled after 10 minutes and retried twice, 5 s and 30 s apart; after that the next caller starts again. Once the pinned file is in place, a `stat` finds it, including after a restart. The idle Daemon pays nothing.

- `agentBrowser/`: vercel-labs/agent-browser (Apache-2.0), the Browser's MCP server (ADR 0092). Bare binaries for darwin arm64/x64, Linux arm64/x64 (glibc and musl) and Windows x64 (keyed `windows-x64`, as `runtimePlatform()` names it); no Chrome is downloaded, since it only attaches over CDP. It is not copied into Polaris, so ATTRIBUTION.md has no entry.
- `agentDesktop/`: vercel-labs/agent-desktop (Apache-2.0), desktop control for agents. The release ships `.tar.gz` archives, each the binary and its helpers (`agent-desktop-macos-helper`, `agent-desktop-linux-clipboard-owner`), for darwin, Linux (glibc only) and Windows, arm64 and x64. The archive is downloaded into `<version>.download/`, verified, unpacked with the Host's `tar` into `<version>.staging/`, checked for the binary's pinned size and renamed to `<version>/`, so a version folder is always complete. Not copied into Polaris either.
- `simulator/`: expo/expo-device-hub (MIT, vendoring serve-sim and serve-emu, Apache-2.0) and callstack/agent-device (MIT), the Simulator's hub and its agents' driver (ADR 0099). npm packages with dependencies, not one binary: the Daemon writes the pinned `package.json` and `bun.lock.txt` and runs `bun install --frozen-lockfile --ignore-scripts` with Bun (`simulator/runtime.ts`: the Daemon itself as `BUN_BE_BUN=1 polaris`, or on a sealed macOS release the pinned Bun below), which checks every tarball against its sha512 and runs no lifecycle scripts; the set is renamed into place with a marker once both entry scripts exist. Only a Host that can run some platform installs it (`simulator/support.ts`, `simulatorCapable`). To bump: change the versions in `pin.ts`, run `bun install` on the same `package.json` in a scratch directory and copy its `bun.lock` over `bun.lock.txt`, then `bun scripts/simulatorLicenses.ts audit` and `bun run licenses`. ATTRIBUTION.md and THIRD_PARTY_NOTICES.md carry its licences.
- `simulator/runtime.ts`, `runtimePin.ts`: Bun itself (MIT, oven-sh/bun), only on a sealed darwin release Daemon, which no longer runs scripts as Bun (ADR 0108). Before the tools install, it downloads Oven's release of its own Bun version into `~/.polaris/tools/bun/<version>/`: the archive is checked against its pinned sha256, the `bun` inside against its own before it is made executable, and the folder is renamed into place last. It keeps Oven's signature, never ours. A Bun upgrade changes the version and every hash in `runtimePin.ts` (the release's `SHASUMS256.txt`); a test fails until it does.
