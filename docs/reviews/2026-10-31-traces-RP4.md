## P9: inspector attach

### P9-1 (P1): a blocked main thread keeps the inspector open past the lease

Every way the bootstrap closes the inspector goes through the main thread. That covers the 1.5 s lease, the capture deadline, losing the control socket and an explicit close. The watchdog Worker sends `Runtime.evaluate` → `entry.close()` over `connectToMainThread` (`traces/attach/bootstrap.mjs.txt:61-71`). The Worker can't stop the listener itself.

Node services inspector messages on the main thread through V8 interrupts. That works while JavaScript runs, so a probe with a busy JS loop closed within 2.7 s. It doesn't work while the thread is blocked in native code: `execSync`, sync fs, crypto or zlib, or a native addon such as better-sqlite3. During that time the TCP listener stays up, and `/json/list` answers. Any local process, other OS users included, can connect and queue `Runtime.evaluate`, and the code runs as soon as the thread unblocks.

So the disclosed "any local process can run code while attached" window is not bounded by the capture duration plus the lease. It is bounded by how long the app blocks, and it outlives the Daemon.

`p9/attach.test.ts` "finding P9-1": approve a 1 s capture, block the target in `execSync('sleep 6')`, close the registry (the Daemon going away), wait 2.5 s, then connect as an outsider. Observed `{ listed: 200, attackerRan: true }`; expected `{ listed: null, attackerRan: false }`.

The Quint `profile_attach` model makes `disconnect`, `endTurn` and `close` set `listening: false` in one step, so it can't express this gap. `profiles/README.md` says shutdown is "independent of the application's main event loop", which holds only for JS loops.

Fix direction: drop the TCP inspector for cooperative targets. The bootstrap's Worker already holds an in-process `inspector.Session` connected to the main thread. Run `Profiler.enable`, `start` and `stop` on that session and stream the profile back over the private Unix socket. That removes:
- the port and the `/json/list` exposure;
- the disclosed residual risk;
- P9-7's URL on stderr.

If a TCP inspector has to stay, the spec needs a state where the inspector is still listening after the Daemon stops, and the window has to be documented as unbounded.

### P9-2 (P2): an app that changes `process.title` can never be attached

`inspectTarget` records `command` from the kernel's argv (`KERN_PROCARGS2`, or `/proc/<pid>/cmdline` on Linux). `recheckTarget` requires it to be unchanged (`target.ts:131,138`). Assigning `process.title` overwrites argv memory. The bootstrap registers at preload time, before app code runs, so any server that renames itself fails every check. Next.js does this: ``process.title = `next-server (v…)` `` in `next/dist/server/lib/start-server.js:180`, and `render-server.js:93` does the same for workers. Many other servers do too.

`registry.get()` fails before the approval card is even shown, with "The process changed while approval was pending." That's misleading, since nothing was pending.

`p9/attach.test.ts` "finding P9-2" reproduces it with a Node server that sets its title.

Fix direction: bind identity to PID, start time, the executable's dev and inode, and the launch token. Those are already in `identity`. Don't compare argv, or keep the argv captured at registration only for display.

### P9-3 (P2): long-running Daemons lose earlier targets after 1024 launches

`TargetRegistry.environment` mints a token per launch environment and evicts the oldest at 1024 (`registry.ts:88`). The watchdog connection must present a token still in `tokens` (`registry.ts:148-150`). `get()` doesn't check this, so the approval card opens normally.

Claude's PreToolUse hook mints a new environment for every Bash command (`harness/claude/traces.ts:78`). So once 1024 Bash commands have run anywhere on the Daemon, a dev server started early is still listed and still opens a card. Then, after the user clicks Allow, it fails with "The target disconnected or the capture expired." The user's approval is spent.

`p9/attach.test.ts` "finding P9-3" reproduces this.

Fix direction: authenticate the watchdog against the registered target's own token (`capture.target.token`), not the global map. Expire tokens with their Agent Session, not first-in-first-out.

### P9-4 (P2): the bootstrap takes over user Workers

`--import` preloads also run in a user's worker threads. The bootstrap enters watchdog mode whenever `workerData?.nonce` is truthy (`bootstrap.mjs.txt:105`). A user Worker with `{ nonce }` in its `workerData` connects to the Daemon and is rejected. Then `close()` calls `parentPort.close()` on the user's Worker (`:71`), and the user's messages never arrive.

`p9/attach.test.ts` "finding P9-4" prints nothing instead of `worker replied`. The same script without the bootstrap, and with `--import /dev/null`, prints `worker replied`.

Fix direction: mark the watchdog with a key only the bootstrap knows, for example a `workerData` property named after the launch token. Or start the watchdog from `eval` source instead of the module URL, so user Workers never match.

### P9-5 (P2): an inspector approval drops In Terminal

`inspector.approvalRequested` is handled at the machine root with `"needs-you"` (`engine/session.ts:487-488`). The `in-terminal` state overrides only `harness.approvalRequested` (`:650-651`). In In Terminal, an attach approval therefore moves the session to Needs-you, and after Allow `backToWork` sets it to Working. Then `terminal.return` is refused, and the Desktop App loses In Terminal while the user is still in the TUI.

`data.approvalRequested` has the same gap, and it predates P9.

`p9/attach.test.ts` "finding P9-5" drives the real decider. A Harness approval stays `in-terminal`; an inspector approval reads `needs-you`.

How a user hits this is PLAUSIBLE rather than shown: Codex live co-attach brings TUI Turns into Polaris, and the MCP `profile` tool is reachable from them.

Fix direction:
- Give `inspector.approvalRequested` and `data.approvalRequested` the same in-terminal override, with no state change.
- Update `session.graph.test.ts` and the Mermaid diagram.
- Make sure upgrade recovery, which is `HANDLED` in In Terminal, withdraws an attach card that is now orphaned.

### P9-6 (P2): the sidebar's attach button fails when the agent is idle

`attach/approval.ts:61,86` requires a working Turn. `AttachButton.tsx` and `RestartButton.tsx:63` always render the button. With the agent idle, which is the natural moment to profile a dev server that is still running, every click returns `E-PROFILE-ATTACH-DENIED` "There is no active turn for this approval."

During a working Turn, the user-initiated card also misbehaves:
- It moves the agent's session to Needs-you, though the Harness isn't waiting.
- The capture is cancelled if the agent's Turn ends (the guard in `capture.ts`).

`p9/attach.test.ts` "finding P9-6" reproduces the idle refusal.

Fix direction: either disable the button with a reason when no Turn is working, or let Daemon-owned approvals exist outside a Turn. The second is a Session machine and spec change, so it is the Lead's or the user's call.

### P9-7 (P3): the inspector URL lands in the app's stderr

`inspector.open` prints `Debugger listening on ws://127.0.0.1:<port>/<uuid>`, then `Debugger attached.` and `Debugger ending on …` (`bootstrap.mjs.txt:85`). The full endpoint, which is the secret for P9-1's window, ends up in:
- the agent's tool output;
- log files;
- the user's terminal;
- any stderr a tool parses.

`p9/attach.test.ts` "finding P9-7" reads those lines from the target's stderr.

Fix direction: P9-1's in-process session removes this. Otherwise the bootstrap must stop Node printing the URL; `--inspect-publish-uid` only takes effect from `NODE_OPTIONS`.

### P9-8 (P3): one socket cap for registrations and watchdogs

Every live registered Node process holds one socket for its lifetime, and the registry refuses connections beyond 256 (`registry.ts:112`). Idle sockets that never register don't time out. With 255 other live Polaris-launched Node processes (test workers, watchers, `npm`/`npx` wrappers across sessions), every capture fails, even of an already-registered target.

`p9/attach.test.ts` "finding P9-8" fails at 255 other sockets and passes at 254.

Fix direction:
- Reserve capacity for watchdogs, or send the watchdog over the target's existing registration socket.
- Time out connections that don't register.

### P9-9 (P3): registration isn't bound to the connecting process

`register` and `watchdog` trust `message.pid` (`registry.ts:148-174`). Neither checks the socket peer's PID (`LOCAL_PEERPID` on macOS, `SO_PEERCRED` on Linux).

Any process holding the inherited token can do this, a bash or Python sibling included:
1. Register the PID of a sibling Node process that has the token but never loaded the bootstrap, for example because a package.json script overwrote `NODE_OPTIONS`.
2. Answer the capture with its own `ws://127.0.0.1:<port>/…` CDP server.

The Daemon then stores the forger's profile under the victim's PID and command. Probe output: `registered as victim: true … daemon would connect its CDP client to ws://127.0.0.1:49725/0123abcd (the forger's server)`.

Impact is limited to a same-user process forging profile data.

Fix direction: require the peer PID to equal `message.pid` for both register and watchdog.

### P9-10 (P3): Always allow on attach cards outside the Desktop App

These surfaces all offer Always allow / Always here for every non-question kind, and all send `Allow{remember:true}`:
- `apps/mobile/src/thread/PendingRequests.tsx:143`;
- the push "approval" category (`apps/mobile/src/push/answer.ts:43-46,58`, chosen in `apps/daemon/src/push/plan.ts:96`);
- `extensions/raycast/src/pending-approvals.tsx:83`.

The machine refuses this for `profileAttach`, so it fails closed, but the user's tap is refused. From a push action, it fails silently.

Fix direction: mirror the Desktop App's `offersAlwaysAllow` in those clients, and add a push category without Always for `profileAttach`.

## P4: Profiles

### P4-1 (P1): restart and shutdown discard the recording they end

Restart stops the process with `killTree(pid, "SIGTERM")` (`traces/profiles/index.ts:614`). Daemon shutdown sends SIGTERM, then SIGKILL (`stopOwned`, `:686-704`). Neither Node nor Bun writes a `--cpu-prof` artifact when killed by a signal. I checked by hand:

```
node --cpu-prof --cpu-prof-dir=D -e "setInterval(()=>{},100)" ; kill -TERM  → exit 143, 0 files
node --cpu-prof --cpu-prof-dir=D -e "setTimeout(()=>{},300)"              → 1 file
```

Bun behaves the same way.

So:
- Every restart turns the recording it ends into `failed`.
- Shutdown loses every in-flight recording.
- A server that never exits by itself, which is the main reason to restart, can never produce a profile through Polaris. Each restart discards the recording that has the data, and the new one completes only on a natural exit.

The contract says profiles "are written on normal process exit", but nothing tells the user or agent that restart discards the current one. The existing restart test never checks the old recording's status.

`p4/profiles.test.ts` "finding P4-1" (Node and Bun) reads `Expected: "completed", Received: "failed"`.

Fix direction: end the process so the runtime flushes its profile.
- One way is a Daemon-owned preload (`--require` for Node, `--preload` for Bun) whose SIGTERM and SIGINT handlers call `process.exit()`.
- Another is to stop the profiler over the inspector before the kill (see P9-1's in-process session).

At shutdown, keep what was flushed and parse it on next start (see P4-2).

### P4-2 (P2): a completion rejected by a full queue is lost

The profile job queue is Host-wide and holds 32 jobs. Only `discard` waits for room; every other job is rejected when it's full (`index.ts:156-161`). Reads fill it: `list`, `get`, and each `watch` subscriber re-listing on every change.

If a process exits while the queue is full, its completion job is rejected at once and the recording is marked `failed` (`:380-395`). The `.cpuprofile` stays on disk, and `get` on a non-completed recording never reparses it (`worker.ts:273-279`). Recordings left `recording` by a Daemon shutdown also have no recovery path.

`p4/profiles.test.ts` "finding P4-2" reads `failed`, with `CPU.….cpuprofile` still in the recording directory. The same scenario without the held queue completes.

Fix direction: always admit completion jobs, as `discard` already is. In `get` and `list`, reparse any recording that is no longer active but still has an artifact.

### P4-3 (P2): retention evicts finished recordings for an active one's bytes

`prune` adds active recordings' bytes to the budget total but skips them when deleting (`worker.ts:144-160`). While an in-flight recording is large, every finished recording in the checkout is deleted, and usage still stays over budget. An active recording grows large easily:
- Test-runner forks inherit `NODE_OPTIONS` and write their own artifacts into its directory. Completion later deletes those anyway (`:201-202`).
- `diskSize` reports `MAX_SAFE_INTEGER` above 4096 entries (`:90`).

`p4/profiles.test.ts` "finding P4-3" sets a 4,000-byte budget and puts an 8,000-byte child artifact in an active recording. Afterwards the list holds only the active id: the finished recording is gone.

Fix direction: leave active recordings out of the byte and count totals, or stop evicting once eviction can't reach the budget.

### P4-4 (P2): four never-exiting commands block profiling on the Host

One cap of 4 covers launches, recordings, parsing and starting across every checkout (`index.ts:414-416`). There is no stop operation: restart only relaunches. Four dev servers or watch-mode runs hold every slot until they exit, and every session in every checkout is refused. The refusal is `E-PROFILE-UNAVAILABLE` "CPU profiling is unavailable.", with the fix "Check the Node or Bun installation and the Daemon's storage, then retry.", which sends the agent after a problem that doesn't exist.

A recording also has no duration cap. At V8's default 1 ms sampling interval, a run of about 33 minutes exceeds 2M samples or 500k frames, and the artifact is then rejected as invalid.

`p4/profiles.test.ts` "finding P4-4" fails on the fix text. A control confirms that the same capture in the other checkout completes when no runners are active.

Fix direction:
- Give the limit its own message, naming the active-capture limit.
- Add a stop (or stop-and-read) operation for owned recordings.
- Consider a per-checkout cap, a maximum recording lifetime, or a coarser sampling interval for long runs.

### P4-5 (P2): `profile`'s `structuredContent` is unbounded

The 16,000-character cap applies only to the text (`apps/daemon/src/mcp/tools/profile.ts:212-215`). `structuredContent` always carries the full `ProfileDetail`, every node and every function.

A probe at the parser's bounds (500k nodes, 200k functions with 200-character names):
- The text was 11,604 characters.
- `structuredContent` serialised to 95,331,944 bytes in one tool result.
- Decoding the `ProfileReply` on the Daemon's main thread (`workerClient.ts:58`) took 158 ms, and stringify another 68 ms.

A normal 3 s capture is 366 KB (P9's probe: 1,173 functions, 3,506 nodes). MCP clients that send `structuredContent` to the model, or limit result size, get the full payload on every call.

Fix direction: in MCP `structuredContent`, omit `nodes` and clip `hotFunctions` to what the text shows, with counts. Keep the full detail on the `profiles.get` RPC.

### P4-6 (P2): parser memory within the advertised bounds

`profileStacks` builds a full root-to-leaf array for every node, O(nodes × depth) (`parser.ts:210-233`). Aggregation spreads one object per depth level per sample (`:137-153`).

| Artifact | Time | Peak RSS |
|---|---|---|
| 17 MB, 200k nodes, depth 250 | 2.1 s | 137 → ~1,300 MiB |
| 200k nodes, depth 1 | 0.5 s | ~430 MiB |
| 12 MB, 2M samples alternating two depth-250 leaves | 10.6 s, then rejected (frame cap) | — |

The profile worker is a thread in the Daemon process, so one in-bounds artifact pushes the Daemon past 1 GB. That's a risk on a Pi 4 or a small VM. A Pi-class CPU may also hit the 60 s worker timeout on large legitimate profiles, which produces `failed` with no retry (P4-2).

Fix direction:
- Memoise stacks through the parent (shared prefixes), or aggregate by walking the tree.
- Update frame durations in place.
- Check a byte and depth budget before materialising.

### P4-7 (P3): restart can kill without relaunching

Restart kills the process, waits for its completion, then calls `launch()`, which re-checks the Host-wide cap of 4 (`index.ts:614-652`). If another capture or attach takes the freed slot during that window, the relaunch fails with `E-PROFILE-UNAVAILABLE` after the user's process is already dead.

Fix direction: reserve the slot (`starting++`) before the kill and hand it to the relaunch.

## P8: compare

### P8-2 (P2): Baseline admits a later Turn's trace by its earliest span

Baseline "before" selects summaries with `start < baselineStart AND turn_id NOT IN (target)` (`traces/compareQuery.ts:115-121`). `summaries.start` is the earliest span start in the trace (`database.ts:127-131`), while `turn_id` comes from the root span's attribution.

Take a trace whose root starts in a later Turn, or after the target starts in a concurrent session. If one of its spans is stamped before the target Turn's start, the trace passes the filter and joins "before" as an earlier-Turn sample. A skewed clock in another container or Host can cause this, as can a span back-dated to enqueue time. Its duration is the whole trace, so it is large. The contract says Baseline is "from earlier Turns" and excludes later traces.

`p8/compare.test.ts` "finding P8-2": expected before `{count:3, p50Ms:110, p95Ms:120}`; observed `{count:4, p50Ms:110, p95Ms:30000}`.

Fix direction: decide earlier or later from the trace's attributed Turn (its start, or its order in the session), or from the root span's start, not the earliest span's start.

### P8-4 (P2): each compare blocks the trace worker for ~¼ s at a full checkout

Each compare runs three statements, `read("a")`, `read("b")` and `newest` (`compareQuery.ts:127-193`), and each re-materialises both CTEs.
- The before-side signature set scans every span of every earlier trace on the matching routes, with `json_extract` on the span JSON plus a parent self-join. The `name` and `parent_name` columns TF2 indexed aren't used.
- No index covers `turn_id`. The plan is `SEARCH summaries USING INDEX summaries_history (checkout=?)`, which scans the checkout's summaries.
- The call is synchronous in the single trace worker (`worker.ts:166-167`), so OTLP flushes and every other trace read wait behind it.

Measured with `bun ../../docs/reviews/2026-10-31-traces-RP4/p8/probe-perf.ts 3000 60 [file]` from `apps/daemon` on an M2 Max at load ~30. The store held 181,800 spans, about the 200 MB per-checkout cap.
- A Baseline compare took 212–216 ms in memory and 273–276 ms on a 265 MB file database, on every call.
- The before-signature scan alone took 258 ms as written, and 112 ms when it used the `name` and `parent_name` columns.

I didn't measure on a Pi; scaling these numbers suggests more than a second there. The Desktop App calls compare on open, on a pick change and at Turn end, not on a timer.

No failing test: a timing threshold would be flaky at this load.

Fix direction:
- Materialise the two sides once (a temporary table, or one statement).
- Read signatures from the `name` and `parent_name` columns.
- Index `summaries(checkout, turn_id)`.
- Optionally cap Baseline to the newest N traces per route.

### P8-3 (P3): a rootless trace counts as a complete sample

With no parentless span, the summary's root is the earliest span (`database.ts:112-116`). `partial` is set only by retention (`retention.ts:126`), and compare counts every row that isn't partial as a complete sample (`compareQuery.ts:170-171,216`). A trace whose root never arrives is grouped under a route named after a child span, for example when the request is still in flight or the agent killed the dev server mid-request. That route reports `after.count 1`, isn't marked partial, and its `slowestNew` is the orphan span itself. In Baseline mode the after side isn't filtered by route, so the phantom route always appears.

`p8/compare.test.ts` "finding P8-3" observes `{route:"pg.query invoices", before:{count:0}, after:{count:1,…}, slowestNew:{name:"pg.query invoices", durationMs:30}}`.

Fix direction: treat a trace with no local root as incomplete. Exclude it from stats and signatures and count it in `partial`. Keep a server or consumer span with a remote parent as a real root, using OTLP's remote-parent flag or the span kind; otherwise every trace with an upstream caller would be excluded.

### P8-1 (P3): compare text can split a surrogate pair

`compareFormat.ts:7-8` runs `inline()`, then `slice(0, 240)`. A name with an astral character at position 239–240, such as an emoji or CJK Extension B, leaves a lone surrogate in the tool's text, which becomes U+FFFD in UTF-8 or is rejected by a strict client. `traceFormat.clipped` already calls `.toWellFormed()` after slicing.

`p8/compare.test.ts` "finding P8-1" observes `isWellFormed()` false.

Fix direction: use `clipped`, or call `.toWellFormed()` after the slice.

## What I checked and found sound

P9:
- **Control channel:** the socket lives in a 0700 `mkdtemp` directory, so other OS users can't connect. Lines are capped at 16 KB on both sides and decoded with Effect Schema. The watchdog nonce is 32 random bytes.
- **Approval freshness:** the machine refuses `Allow{remember:true}`, `Allow` with a `dataScope`, and `Answer`. Neither `harness.` nor `data.approvalRequested` can carry `profileAttach`. Each capture gets a fresh random RequestId, and the subscription filters on it. A finalizer withdraws the request. `daemon.recover` withdraws pending requests after a restart or upgrade, outside In Terminal (see P9-5). `ApprovalPolicy.decide` applies only to Harness approvals. The reactor uses `committed.before`, so the response never reaches a Harness. A stale or replayed decision can't satisfy a new capture.
- **Binding:** the card shows the PID, command and seconds, and the capture uses the same seconds (watchdog cap 30 s + 5 s). `targets.open` re-checks the PID, start time and executable dev/inode, and that it's the same registry entry. A target is removed when its process exits, so PID reuse can't redirect a capture. Targets are scoped to their session, and the Turn guard re-runs on every session change.
- **Inspector:** binds 127.0.0.1 on port 0, never 9229, with no signals. The returned URL is validated. An inspector that is already open is refused and left alone. `inspector.close()` disconnects connected clients. A busy JS loop doesn't defeat the watchdog.
- **The Daemon as CDP client:** it sends only fixed expressions, caps messages at 64 MB, and checks the PID and Bun identity.
- **`NODE_OPTIONS`:** the user's options are kept. `--disable-sigusr1`, `--permission`, Bun and Windows are skipped.
- **Startup cost:** +4.76 ms (28.67 → 33.43 ms medians over 20 alternating pairs), matching the claim.
- **Desktop:** `rows.tsx` and `decide.ts` send `Allow{remember:false}` with the card's own id, and Always allow is absent.

P4:
- **Restart identity:** restart takes only a live retained handle. It re-checks exit and signal codes after every await, requires the same canonical checkout, and re-checks the cwd (realpath containment), session policy and Trust before the kill. It relaunches the exact stored argv in the stored cwd, with a fresh overlay from the original source environment. Concurrent restarts are refused. Unknown, gone and foreign-checkout PIDs return `E-PROFILE-PROCESS-NOT-OWNED`.
- **Authorization:** Reviewer, plan and read-only sessions can't execute. Storage is keyed by `sha256(canonical checkout)`. Ids must match `^[0-9a-f-]{36}$`, so there's no path traversal.
- **argv:** there is no shell. `--cpu-prof*` and `--diagnostic-dir` are refused in argv and in `NODE_OPTIONS`/`BUN_OPTIONS`.
- **File bounds:** size is checked with `fstat` (O_NOFOLLOW, nlink 1, 64 MiB) before any read. Temporary files are removed in `finally`. Child artifacts are removed at completion, and every artifact on a parse failure. Orphan directories are pruned, and the 7-day and 200-recording limits apply.
- **Parser:** duplicate ids, multiple parents, cycles and depth over 256 are rejected without looping. Sample and timeDelta lengths are checked. Recursion counts inclusive time once per sample.
- **Worker:** the 60 s timeout ends a hung worker. Shutdown fails queued jobs fast and waits only for the one in flight. No idle timers.
- **Scrubbing:** `--token`, `--api-key=`, `--password`, `GITHUB_TOKEN=`, `AWS_SECRET_ACCESS_KEY=`, Bearer tokens and JWTs, `user:pass@` URLs and `?token=` are all removed.
- **MCP text:** every branch is capped at 16,000 characters. Labels are clipped to 256 characters, with control and bidi characters stripped.

P8:
- **Scoping:** Turn and Turns selectors resolve only against the caller session's Turns. Another session's Turn gets the same `E-TRACE-NOT-FOUND` as an unknown one. Trace prefixes are scoped to the checkout and allow hex only, so LIKE wildcards can't be injected.
- **Selector rules:** Baseline is accepted only as `a` against Turn or Turns, and Trace only with Trace. Everything else is `E-INPUT`.
- **Turn ranges (UF8):** inclusive bounds. A reversed range is `E-INPUT`, and a foreign range end is `NOT-FOUND`. Baseline uses the range's first Turn's start and excludes every Turn in the range.
- **Time units:** Turn starts are converted from ms to ns, and summary starts are zero-padded ns, so the text comparison is consistent.
- **Percentiles:** nearest-rank `ceil(n·p) − 1` is correct (n = 3 → indices 1 and 2; n = 4 → 1 and 3; n = 20 → p95 index 18). A float check up to n = 100,000 found no off-by-one. The three-sample guard counts only complete samples, on both sides.
- **slowestNew:** the parent-name match is NULL-safe, and ties break deterministically.
- **MCP text:** with 1, 40 and 500 routes, 5,000-character names and bidi characters, the text stayed at 16,000 characters or fewer (14,998 at most), with the omitted-routes footer intact. JSON keeps every route.
