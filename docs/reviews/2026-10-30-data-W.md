prefix and drops what it creates, including the `dblink` extension and the extra MySQL database.

**Verdict.** The approval mechanics hold. A write approval is one-shot and bound to its session,
Turn, source, target, SQL, parameters and reason. Turn end and recovery deny pending cards.
Concurrent retries can't run twice. A one-request read grant never authorises execute, and grid
commits are atomic. What doesn't hold is what surrounds the approval:

- **F1:** the dry run runs before any approval, and with the right schema it commits writes
  elsewhere.
- **F2:** a Local source set to "writes off" still dry-runs and asks.
- **F3:** a write that committed can be reported as cancelled.
- **F4:** the card can't show the user what they're approving.

F5 to F10 are P2s: Local write policy carrying over to Remote, same-count drift, primary-key
assignments that get past the check, MySQL writes to other databases, secrets persisted from
previews, and spec coverage. F11 to F14 are P3s.

### F1 · P1 · The unapproved dry run commits external effects

`execute` runs the statement in a writable transaction as soon as the agent calls it (with no
approval for a Local source, or with remembered read approval and writes `ask` for a Remote one),
then rolls back. Rollback undoes only the target database's transactional rows. Probe
`rw.effects.probe.test.ts`, all as `postgres`/`root`, all with `dryRun: true`:

| # | Engine | Setup that already exists in the schema | Statement the agent sends | Left behind after the "rolled back" dry run |
|---|---|---|---|---|
| E3 | Postgres | `dblink` installed; `wrap()` = `SELECT dblink_exec(…INSERT INTO audit…)`, `SECURITY INVOKER` | `UPDATE t SET v = wrap() WHERE id = 1` | **audit row `wrapper` committed** |
| E4 | Postgres | `AFTER UPDATE` trigger calling `dblink_exec` | `UPDATE t SET v = 5 WHERE id = 2` (no function in the text) | **audit row `trigger` committed** |
| E8 | MySQL | InnoDB target, `AFTER UPDATE` trigger inserting into a MyISAM log | `UPDATE t SET v = 5 WHERE id = 1` | **MyISAM row `trigger`** |
| E9 | MySQL | stored function `f()` inserting into MyISAM | `UPDATE t SET v = f() WHERE id = 2` | **MyISAM row `function`** |
| E1 | Postgres | `serial` key | `INSERT INTO t(v) VALUES (9)` | sequence 2 → 3 (disclosed) |
| E7 | MySQL | `AUTO_INCREMENT` | `INSERT INTO t(v) VALUES (9)` | `AUTO_INCREMENT` 4 → 5 (disclosed) |
| E10 | MySQL | `AUTO_INCREMENT` key | `UPDATE t SET ID = id + 100` (refused after the preview) | `AUTO_INCREMENT` 5 → 104 |

XF's catalog guard (`functionGuard.ts:13-24`) flags only functions that are `SECURITY DEFINER`
*and* owned by a superuser, or that belong to the `dblink`/`postgres_fdw`/`adminpack` extensions.
A plain user function that calls `dblink_exec` passes, and triggers are never looked at.
`writeTable.ts:55` checks InnoDB for the named target only, while ADR 0091 refuses non-InnoDB
targets because their writes survive rollback; a trigger or function reaches them anyway. The
card's note ("Sequence and external side effects may survive rollback") is shown only after the
effect has happened, and only to the user, never as a gate.

Held: a trigger taking `pg_advisory_lock` did not leave the lock held after the preview (E5),
because XF's session release works for writes too. Postgres `NOTIFY` is transactional.

Suggested fix:

1. Before the dry run, refuse (or require approval) when the target has triggers
   (`pg_trigger` excluding internal ones; `information_schema.TRIGGERS`) or the statement calls a
   non-built-in function. On MySQL, refuse if any trigger or routine reachable from the target
   writes a non-InnoDB table; simpler, refuse any trigger or stored-function call.
2. Extend the catalog guard to user functions whose body mentions `dblink`, and to any function
   not `IMMUTABLE`/`STABLE` that isn't in `pg_catalog`.
3. Say on the card, before Approve, which triggers fire on the target.
4. A restricted database role remains the real boundary (ADR 0091). Warn when the Data Source
   user can execute `dblink*` or is a superuser.

### F2 · P1 · "Writes off" isn't enforced on a Local source

The Desktop offers `writes: off` on every source and labels it "Agents read · writes off" and
"Read only" (`apps/desktop/src/renderer/features/data/model/source.ts:110-125`).
`writeQueries.ts:54-61` checks `access.writes` only when `locality === "remote"`. Probe
`rw.policy.probe.test.ts` P1, with the production `DataQueries`:

1. `approvals.change(localSource, "off")` → `approvals.read` returns `{access: "read", writes: "off"}`.
2. `execute` `INSERT INTO t(v) VALUES (1)` → **`DataApprovalRequired`**: a write card opened.
3. The dry run ran: the table's sequence moved 1 → 2. The Query Log holds `dry-run` and
   `waiting-approval` entries.

With F1, "Read only" doesn't stop the unapproved dry run's side effects either.

Suggested fix: deny `execute` with `E-DATA-DENIED` ("Writes are off for this data source") when
`access.writes === "off"` on either locality, before resolving the connection, and refuse
`data.edits.commit` likewise. Add the Local case to `writeRemote.test.ts` and the spec.

### F3 · P1 · A committed write can be reported as cancelled

`executeTransaction` checks `active.stopped` *after* `connection.begin` has resolved, that is
after COMMIT succeeded (`execution.ts:322-327`). An abort (Turn end, Interrupt, the 30 s
deadline, an MCP cancel) that fires while COMMIT runs sends `pg_cancel_backend` or `KILL QUERY`.
If COMMIT completes first, the cancel finds an idle connection, yet the call still throws
`E-DATA-CANCELLED` or `E-DATA-TIMEOUT`.

Probe `rw.run.probe.test.ts` R2 (Postgres): a deferred constraint trigger keeps COMMIT busy for
1.5 s and absorbs the cancel, like any slow commit that outlasts the cancel's round trip. Abort
at 500 ms:

- `executeWrite(… dryRun: false, expected: 1)` → **`E-DATA-CANCELLED The query was cancelled.`**
  with the fix "Run it again when needed."
- The row afterwards: **`v = 42`**, committed.

Through `writeQueries`, the error runs `logged`'s `tapError`, so the Query Log entry says
`failed` ("The query was cancelled."). Through Turn end, `writeTurn.ts` interrupts the effect and
the entry says `cancelled`. `approvals.writes.finish` never runs, so the request stays `started`.
A same-key retry gets "outcome may be unknown". But the agent's first answer is a definite
cancellation with a "run it again" fix, and a retry under a new `requestId`, or without one in a
new Turn, writes twice. The spec forbids this state: replaying the observed outcome
(`rw.r2-trace.json`: execute, `value: 42`, `phase: "failed"`) is rejected ("Data write replay
rejected", `actualWriteTest failed`). No test records it.

Suggested fix: once COMMIT has been sent, never map an abort to a definite outcome. Return
`E-DATA-UNKNOWN` ("The write may have committed. Check the Query Log and the database before
retrying."), and record a Query Log state such as `unknown`. Clear `stopped` if COMMIT resolved
successfully, then treat the write as completed and call `finish`. Add the unknown outcome to
`data_writes` and a trace step for it.

### F4 · P1 · The card can't show what the user approves

- **Parameters.** `approvals.writes.open` stores `sql`, `reason`, counts and preview rows, but
  never the parameter values (`writeQueries.ts:204-218`). The fingerprint hashes them, so the
  binding holds, yet the user can't see them. For `INSERT INTO users(email, role) VALUES ($1, $2)`
  with `["x@y", "admin"]`, the card reads "Run 1-row write · Dry run · rolled back · 1 rows" plus
  the SQL and the agent's `reason`.
- **INSERT has no rows.** `beforeRows` and `afterRows` run only for UPDATE/DELETE (E1, E6, E7:
  `before: []`). On a table with a primary key the note still says "Up to 20 rows, read by
  primary key" while showing none.
- **No Client renders the preview.** `grep -rln dataWrite apps packages extensions` finds only
  the protocol, the spec README and the Daemon. The Desktop shows a generic tool card with
  `title` and `detail`, so the before/after rows, `columns` and `note` never reach the user.
  W disclosed that Desktop write-card acceptance wasn't done; this records the result.

The agent writes the `reason`. With bound parameters, the agent's own text is the only
description of the values the user sees.

Suggested fix: carry scrubbed parameter values (or, Remote, a rendered preview of the statement
with values) in `dataWrite`. For INSERT, read back the inserted rows inside the dry run (by key,
or as `RETURNING` captured internally). Render `dataWrite` in the Desktop and Mobile approval
cards before shipping `execute`. Make the note match what's shown.

### F5 · P2 · A Local write policy carries over to Remote

`ApprovalStore.read` returns `writes: exact?.writes ?? (local ? "ask" : "off")`
(`approvalStore.ts:141`). `change()` writes `writes ?? current.writes` into the exact target's
row (`:160-164`), even for a revoke. A Local source's default `ask` therefore becomes a stored
`ask` the first time the user changes anything on it. Probe `rw.policy.probe.test.ts` P2:

1. Local source: the user only revokes it (`change(local, undefined, true)`). Writes were never
   touched.
2. The same target turns Remote (ADR 0091's tunnel-on-localhost case). `read` →
   `{access: "needs-approval", writes: "ask"}`.
3. The agent asks to read; the user approves with `remember: true` → `{access: "approved", writes: "ask"}`.
4. `execute` → **`DataApprovalRequired`**: the dry run ran on the Remote target.
5. Control: a Remote target that was never Local, with the same remembered read approval →
   `writes: "off"` → `E-DATA-DENIED Writes aren't allowed on this remote data source.`

W's regression (`writeRemote.test.ts`) covers `change(local, "ask")` followed by a one-request
grant, but not a remembered one. A per-statement approval still stands, which keeps this a P2.
With F1, though, the dry run alone can have effects.

Suggested fix: store writes only when the user sets them, with locality: `writes_local` and
`writes_remote`, or a row only written by an explicit writes change. Never copy a default into a
row. This is X F1's shape for reads.

### F6 · P2 · Same count, different rows

`write()` compares only `affected` to the previewed count (`writeExecution.ts:252`). The real
run reads its own before rows and discards them. Probe `rw.run.probe.test.ts` R1, identical on
both engines:

1. Rows `1 stale`, `2 stale`, `3 live`. Preview of `DELETE FROM t WHERE status = 'stale'`:
   affected 2, rows `[1, 2]`. This is what the user approves.
2. Before approval the app marks 1 `live` and 3 `stale`.
3. Real run: affected 2, the drift check passes, **rows 2 and 3 deleted**. Row 3 was never shown;
   row 1, which the user agreed to delete, survives.

The approval can wait for as long as the Turn lasts, so the gap isn't milliseconds.

Suggested fix: when the preview had a primary key and showed every affected row (≤ 20), compare
the real run's before keys with the approved ones and roll back on any difference. Otherwise,
hash the full affected key set in the dry run (`SELECT key … WHERE …` without the 20 cap,
bounded) and compare. Say on the card when only the count is bound.

### F7 · P2 · Primary-key assignments get past the check

The decision says primary-key assignments are refused. Two ways around it (probe E6, E10, E11):

- **MySQL case.** `updatedColumns` returns MySQL names as written (`writeSql.ts:37`) and
  `table.primaryKey.includes(column)` is case-sensitive, so `SET ID = …` isn't recognised on a
  key named `id`; the control `SET id = id` is refused. The after-row lookup catches a changed
  key only within the first 20 preview rows. `UPDATE t SET ID = CASE WHEN id > 120 THEN id + 1000 ELSE id END`
  on 28 rows: the preview showed 20 unchanged rows, both runs passed, and **8 keys moved to
  1121–1128**.
- **Upserts.** The check runs for `UPDATE` only. Postgres
  `INSERT … ON CONFLICT (id) DO UPDATE SET id = 777` committed (ids `[2, 777]`), and MySQL
  `INSERT … ON DUPLICATE KEY UPDATE id = 555` committed (id 1 → 555). Both previews showed no
  rows, and MySQL reported `affected: 2` for one row ("Run 2-row write").

Suggested fix: compare names case-insensitively on MySQL (and unquoted on Postgres). Refuse
`ON CONFLICT … DO UPDATE` and `ON DUPLICATE KEY UPDATE` under ENG-669 until they get a proper
preview, or run the PK-assignment check on their SET lists too.

### F8 · P2 · MySQL writes outside the approved database

`writeTable` resolves `target.schema ?? source.database` (`writeTable.ts:32`), and on MySQL a
schema is a database. The target key that remembered approvals and writes policy bind to is
`[engine, host, port, database, user]`, but the statement can name any database on that server.
Probe E12: with a source on `ledger`, `UPDATE rw_…_db.acct SET bal = 0 WHERE id = 1` previewed,
committed, and changed the other database (`bal 100 → 0`). The result's `target` names the other
schema, but every policy check used `ledger`.

A Remote server where the user allowed writes on `staging` can be written in `prod` on the same
server, behind a card that says "staging". The SQL text does show the name, and a per-statement
approval is still required.

Suggested fix: on MySQL, refuse a qualified target whose schema isn't `source.database` (and
subqueries naming other databases, if reads should match), or key write policy by the database
actually written.

### F9 · P2 · Preview rows are persisted and broadcast

`cappedPreview` scrubs only the connection's own credentials. Up to 20 before and 20 after rows
go into `ApprovalRequest.dataWrite`, which is committed as an `ApprovalRequested` event. That
event is durable in the event store, replayed to every Client's session feed (Desktop, Mobile,
paired devices) and kept after the Turn. Probe E2: `UPDATE t SET v = v + 1 WHERE id = 1` →
`before: [[1, 0, "tok_live_SECRET123"]]`, column `api_token`. A read Query doesn't do this:
only its SQL is logged, and its rows go to the agent but not into the event log.

Suggested fix: keep preview rows out of the event: store them in `data.sqlite` keyed by the
request id with the Query Log's retention, and fetch them for the card. Redact columns whose
names match the existing `sensitive` pattern (`dataFormat.ts`) on the card as well as for agents.

### F10 · P2 · Spec, model-based test and replay coverage

- `data_writes` (`polaris.qnt:1288`) has one write, one session and one target. It has no
  writes policy, locality, request keys or second session, so F2 and F5 are outside the model.
- `rollbackPreviewTest` and safety treat `value`, the target row, as the only effect of a dry
  run. F1's effects can't be stated.
- `execute(n)` is either completed or failed. There is no "committed, but the client saw an
  error" state, so F3 is unrepresentable, and replaying it is rejected (above).
- `endTurn` maps `started` to `denied` (`:1308-1310`), but `WriteApprovalStore` never denies a
  started write (only `pending`, via `ApprovalWithdrawn`). Model and code disagree there.
- Row identity is the count (`affected == expected`), so F6 is outside the model.
- Replay fidelity: `writes.real.test.ts:115-170` pushes `phase` literals (`"pending"`,
  `"approved"`, `"completed"`) chosen by the test, not read from `data_write_requests`. `value`
  is the one target cell. Only one path is traced: preview, approve, execute, retry. The deny
  and Turn-end steps run in the same test but aren't recorded. Both recorded traces replay 9/9
  here, but a regression in the store's status would still replay.
- `dataWrites.model.test.ts` drives the real machine and `ApprovalStore` with one fixed request.
  It checks one-shot consumption well, but never the SQL path, request keys or policy.

Suggested fix: add `writesPolicy`, `locality` and an `unknown` outcome to `data_writes`. Read
`phase` from `WriteApprovalStore.find` when recording traces, and record deny, Turn end and
drift. Add F2, F3 and F5 as model-test actions or `test.todo`s in `findings.test.ts`.

### F11 · P3 · Duplicate grid edits through mixed key types

`editStatements` groups by `JSON.stringify(edit.key)` (`writeEdits.ts:16`). Probe G3b, both
engines: edits `{key: [1, "x"], v: 1}` and `{key: ["1", "x"], v: 2}` produce two UPDATEs of the
same row, the last wins (`v = 2`), and the result says `affected: 2`. Exact duplicates are refused
(G3). A BigInt key read as `{_tag: "BigInt", value: "1"}` next to a typed `1` would do the same.
Suggested fix: after the batch, refuse if the database's matched row set has fewer distinct keys
than groups, or normalise keys by column type before grouping.

### F12 · P3 · Binary primary keys can't be edited

Probe G9: Postgres `bytea` keys read as `{_tag: "Bytes"}`, and `bindValues` refuses them as
display-only. A MySQL `BINARY(16)` key (a common UUID layout) reads back as **`null`** through the
read path, so the grid sends a null key and the commit matches 0 rows. Both fail closed. The
MySQL `null` is a read-path decoding issue (XF/X), recorded here because it reaches the grid.
Suggested fix: carry an opaque, Daemon-verifiable key token for binary keys, and decode MySQL
binary columns as `Bytes`.

### F13 · P3 · One lock serialises all writes

`writeQueries` makes one `Semaphore(1)` (`writeQueries.ts:48`) and holds it across
`duringWriteTurn(… execute(input))`, including the 30 s dry run and the 30 s real run. A slow
preview in one Agent Session on source A blocks every other session's `execute` on source B.
Their 55 s MCP budget then runs out ("Waiting…"). Suggested fix: key the lock by
`(sessionId, requestKey ?? fingerprint)`; the durable compare-and-set already prevents double
execution.

### F14 · P3 · Query Log after a crash, and deny copy

- A Daemon crash after `claim` leaves the request `started` (correct: retries say "outcome may be
  unknown"), but the Query Log entry stays `running` forever. Nothing in `queryLog.ts` settles
  running entries on start. Show it as "outcome unknown" after recovery.
- A write denied without a reason returns "The user denied this data source."
  (`approvals.ts:97`); for a write it should say "The user denied this write."

## What was attacked and held

**Approval binding** (by reading `writeQueries.ts`, `writeIdentity.ts`, and the passing tests):

- Without a `requestId`, the fingerprint hashes session, Turn, source id, target key, SQL,
  params and reason, so an approval for statement A can't run B, and changed params need a new
  card. With a `requestId`, the key is `(session, requestId)` and `requestHash` covers source,
  SQL, params and reason; a changed payload is refused before anything runs
  (`writes.real.test.ts`, passing).
- Approval reuse across sessions: impossible, the key includes the session. Across Turns: an
  uncompleted approval is refused in a later Turn, and a completed receipt is returned
  (decided).
- A source re-pointed between approval and run: `resolve` runs again before `claim`, and a
  different target key is refused. A target that turns Remote between approval and run is
  re-checked for writes and remembered read access, and DDL is refused on Remote at execution.
- A changed `.env` password with the same target runs with the new credentials. The approval was
  for the target, not the credential, which is correct.
- Races: two concurrent `execute`s on one key → one run, one receipt (passing test). `claim` is
  a SQLite compare-and-set.
- A one-request read grant never authorises execute (`writeRemote.test.ts`), and a Harness can't
  forge or answer a write card (`writeApprovals.test.ts`). Both pass.

**Deny reason:** the user's reason reaches the agent as `E-DATA-DENIED <reason>`
(`writes.real.test.ts`: "Use staging"). It is scrubbed and control characters are escaped by
`safeDataText` at the MCP boundary (`mcp/tools/data.ts:84-88`).

**Decided limits held** on the probes: MySQL DDL and non-InnoDB targets refused; Remote DDL
refused; joins, CTEs, aliases, RETURNING, ORDER/LIMIT and tuple SET refused (`writeSql.test.ts`,
passing); lowercase PK assignment refused (E10 control); `foundRows` on MySQL (grid no-op
updates count 1). The exceptions are F7 and F8.

**Grid commits** (probe `rw.edits.probe.test.ts`, both engines): composite keys commit; a key
list in the wrong order is refused ("primary key does not match"); a NULL key → 0 rows → whole
batch rolled back; an exact duplicate cell is refused; a key-column edit is refused; 10,001 edits
fail schema decoding. A mid-batch CHECK violation rolled back the earlier edit (G4: row
unchanged). MySQL strict mode refused a numeric key against a `VARCHAR` key ("Truncated incorrect
DOUBLE value"), and Postgres refused the operator, so no coercion matched a wrong row. Timestamp
keys round-trip from the read path on both engines (G8).

**Secrets:** the SQL in the Query Log, the card and the approval payload is scrubbed with the
connection's known credentials. Parameters aren't stored anywhere (which is also F4). Error text
goes through `queryError` with known credentials.

**Cancellation and deadline before COMMIT:** `writeTurn.test.ts` (Turn end interrupts and
awaits rollback) passes, and an abort during the statement rolls back. F3 is only the
COMMIT-in-flight window.

**Daemon restart with a pending approval:** recovery withdraws it as denied, and a later call
gets `E-DATA-DENIED` (`writeApprovals.test.ts`: `harness.turnEnded`, `session.stopped` and
recovery endings, passing). A crash after COMMIT leaves `started`, so a retry is refused as
"outcome may be unknown", never re-run (F14 for the log).

**Idle cost:** no timer, interval or polling in `write*.ts`. The only `setTimeout` is the
per-transaction deadline in `executeTransaction`, cleared in `finally`. The write projection
reuses the approval store's commit-driven sync. Idle bench not rerun (no change to anything on
a timer).
