# Adversarial review: M, Data MCP tools and outside-Polaris detection (ENG-644)

Reviewed: `c55114cf`, merged with D in `075b52e3` on the integration branch, diffed against
`5bfef92f`. Read against `docs/specs/data-tools-v1.md`, ADR 0091 and CONTEXT.md → Data.
Reviewer: RM, Opus 5.5, 2026-10-30. No product code changed.

I used the tools for real from a Claude session (Sonnet, Claude Code 2.1.314) and a Codex session
(gpt-6.1-sol, Codex 0.164.0). Each ran in a dev Daemon with a throwaway `POLARIS_HOME` under
`/tmp/pls-*`, against a throwaway `postgres:16` in OrbStack seeded with hostile rows and names.
X isn't merged, so `DataQueries` is still a stub. The second pair of runs used a review-only
`DataQueries`: `Bun.SQL` in a read-only transaction, with `describe` left unsupported. It was
wired into the dev Daemon and removed before commit (see Repro). Any finding that depends on it
says so.

**Verdict.** In the real Daemon the tools can't run yet: every call, including `data_sources`,
returns `E-NOT-READY`, and outside detection never starts (F1). With that wired, the scrubbing
works for the exact password and URL. It leaks other forms of the same password (F2), and its URL
regex can freeze the Daemon for minutes on a single large value (F3). Claude never sees the text
output the spec designs for (F4). The outside matcher misses every Codex command (F5). F7 and F8
(the approval wait against cancellation and Codex's 60 s timeout) need decisions shared with X.

### F1 · P1 · The real Daemon never gives the tools or the reactor a `DataQueries`

`serve.ts:163` provides `DataQueries.layer` only to `DataRpcsLive`. `engineServices` (`:145`)
merges `DataSources` but not `DataQueries`. Both `mcpHttp` (`http.ts:141`) and the Engine
reactors (`reactors.ts:64-65`) look it up with `Effect.serviceOption(DataQueries)`, get `None`,
and quietly skip it. Every test provides both services itself, so the suites pass.

Failing scenario (live, first Claude run on the unmodified merge `075b52e3`): `data_sources {}`,
both `describe` calls and all five `query` calls returned
`E-NOT-READY: Data isn't connected on this host`. The two `psql` commands that followed weren't
recorded either, because the subscriber was never started. It is P1 rather than P0 because the
failure is safe, but the lane does nothing in the product. X will replace the stub at this same
line, so the bug survives X unless the wiring changes. Suggested fix: `Layer.provideMerge` one
`DataQueries` into `engineServices`, and give `DataRpcsLive` that same instance (approvals and
the Query Log have to be shared). Add a test that starts the composed `daemonHandlers` and calls
`data_sources` over MCP.

The opt-in real-Postgres test is now runnable: `POLARIS_DATA_POSTGRES_URL=… bun test
src/mcp/tools/data.postgres.test.ts` passes `data_sources` and fails at `describe` with `isError`,
because of the stub. That's expected until X lands.

### F2 · P1 · Other forms of the source's own password leak

`knownFromUrl` adds three strings: the whole URL, the decoded password, and
`encodeURIComponent(password)`. `scrubKnown` drops anything shorter than 4 characters. Repro L1,
with the scrubbing done through the real tool:

| URL in `.env` | Value in a cell | Leaks |
|---|---|---|
| `postgres://app:hunter2-Secret!@…` (live) | `hunter2-Secret%21` | **yes**, in both Claude's and Codex's output |
| `postgres://app:p%40ss%2Fw0rd%21x@…` | `p%40ss%2Fw0rd%21x` (as written) | yes |
| same | `p%40ss%2fw0rd%21x` (lowercase hex) | yes |
| `postgres://app@…/ledger?password=qpSecret99` | `qpSecret99` | yes. D's `parseConnection` honours `?password=`; `knownFromUrl` reads only `url.password` |
| `postgres://app:pw1@…` | `pw1` | yes (under 4 characters) |
| `postgres://app:20261030@…` | the number `20261030` | yes. `dataValue` returns numbers without scrubbing |
| `postgres://app:p%40ss%2Fw0rd%21x@…` | `p@ss/w0rd!x` (decoded) | no |

Suggested fix: build the known list from `resolve().connection.password`, which D already
returns, rather than from the URL. Add the forms as written and as `encodeURIComponent`
(upper- and lowercase hex, plus `%21`-style encoding of `!'()*`), and scrub them
case-insensitively. Scrub the string form of numbers, bigints and dates as well. A password
under 4 characters can't be scrubbed safely without blanking ordinary text. Say so in the tool
description, or refuse to show a cell that equals the password exactly.

### F3 · P1 · A single large value can freeze the Daemon

`safeDataText` runs `/\b[a-z][a-z\d+.-]*:\/\/[^\s<>"']+/gi` over the whole string, then `clip`
shortens it to 200 characters. With no `://` in the value, each word boundary scans forward to
the end and backtracks, so the work is quadratic. The engine is JavaScriptCore (Bun 1.4.4), and
the call is synchronous on the Daemon's only JavaScript thread.

| `"a.".repeat(n/2)` | ms |
|---|---|
| 100,000 chars | 1,155 |
| 200,000 | 4,596 |
| 400,000 | 18,482 |

Failing scenario: an agent runs `query {sql: "select repeat('a.', 500000)"}`, or reads any log or
text column of about 1 MB with dotted words. That freezes every Agent Session, Client feed and
terminal on the Host for about two minutes per value. Suggested fix: clip to a bound (for
example 4× the 200-character limit) before the regex runs, and make the scheme part
possessive-safe: anchor on `://` and scan backwards a bounded distance. Add a timing test with a
1 MB value.

### F4 · P1 · Claude reads `structuredContent`, not the text

Claude Code hands the model `structuredContent` JSON whenever a successful result carries it.
The live Claude transcript recorded `{"sources":[{"name":"app",…}]}` for `data_sources` and the
raw JSON for every `query`. Codex, given the same results, read the aligned text. So for Claude:

- The 16k cap doesn't hold: the `wide` query reached Claude as about 18.9k characters of JSON.
  `structuredContent` itself is never capped; repro I2 has a 20k column name in it.
- The truncation sentence never arrives. For `select … from invoices`, Claude got 200 rows with
  `"rowCount":300,"truncated":true` and reported "the count doesn't match the rows", which is the
  confused-agent outcome the sentence exists to prevent. Codex got
  `200 of 300 rows; add a WHERE or an aggregate`.
- Errors with `isError` reached Claude as text, so the error path holds.

Suggested fix (a decision for the Lead): either put the human sentence into `structuredContent`
(`note: "200 of 300 rows; add a WHERE or an aggregate"`, `returned`, `total`), which CF's
returned/total metadata makes natural, or leave `structuredContent` off on the Claude binding.
Cap the JSON at the same 16k in both cases.

### F5 · P1 · The outside-Polaris matcher misses every Codex command

Codex reports each shell Tool Call as `/bin/zsh -lc '<script>'`. `commands()` reads the script as
one quoted argument to `zsh`, so `invocation()` never sees `psql`. In the live Codex run, both
`psql` commands ran against the checkout's database and neither was recorded. In the Claude run,
the same two commands were recorded (`/tmp/rm-outside.log` holds 2 entries, both from
`smoke-claude`).

Unit matrix (repro O; source `app@localhost:5432/ledger`):

| Command | Result |
|---|---|
| `PGPASSWORD=… psql -h localhost -U app -d ledger` | match |
| `psql "$DATABASE_URL"`, `psql $DATABASE_URL`, `psql "${DATABASE_URL}" < f`, `pg_dump -Fc "$DATABASE_URL"`, `psql --dbname=$DATABASE_URL`, `psql postgres://app@localhost/ledger` | match |
| `bash -lc 'psql "$DATABASE_URL"'`, `/bin/zsh -lc 'psql $DATABASE_URL'` | **miss** |
| `docker exec -it pg psql -U app ledger`, `docker compose exec db psql …` | miss |
| `PGPASSWORD=… psql -h localhost -U app ledger` (positional dbname) | miss |
| `PGPASSWORD=… psql -h 127.0.0.1 -U app -d ledger` when the source host is `localhost` | miss |
| `psql -h localhost -d ledger` (user from `$USER`/`PGUSER`) | miss |
| `PGHOST=localhost PGUSER=app PGDATABASE=ledger psql` | miss |
| `sudo -u postgres psql ledger` (`-u` read as the program) | miss |
| `mysql --defaults-file=.my.cnf ledger` | miss |
| `bun -e 'await Bun.sql\`select 1\`'` (reads `DATABASE_URL` implicitly) | miss |
| `npx prisma db execute --url "$DATABASE_URL"`, `pgcli $DATABASE_URL` | miss |
| `node -e 'console.log(process.env.DATABASE_URL)'` | **match (false positive)**: recorded as a Query though nothing touched the database |
| `echo psql $DATABASE_URL`, `grep … && psql --version`, `cat .env \| grep DATABASE_URL` | miss (correct) |

Suggested fix: unwrap `sh|bash|zsh -c/-lc <script>` before tokenizing; the Codex case alone
covers half the Harnesses. Treat `docker exec|compose exec … <client>` and `sudo [-u x]` as
prefixes. Compare hosts as a set (`localhost`, `127.0.0.1`, `::1`). Accept a positional dbname,
`PG*`/`MYSQL_*` env assignments, and `$USER` as the default user. The spec calls this
"best-effort", but Codex is half the Harness pair it ships for.

### F6 · P2 · Credentials Polaris doesn't know pass `safeDataText`

The generic pass catches `scheme://…` and `password|passwd|pwd|token|secret` followed by `:` or
`=`, but only on a word boundary. Repro L2 and L3 (the same applies to `DataError.message`):

```
"PGPASSWORD=othersecret psql -h db"     → unchanged ("\bpassword" doesn't match inside PGPASSWORD)
"MYSQL_PWD=othersecret"                 → unchanged
"{\"password\":\"othersecret\"}"        → unchanged (the quote before ":" breaks the pattern)
"app:othersecret@db.internal:5432/app"  → unchanged (no scheme)
"postgres://app:ab'othersecret@db/app"  → "[redacted URL]'othersecret@db/app"
"postgres://app:ab othersecret@db/app"  → "[redacted URL] othersecret@db/app"
"pass=othersecret", "-pothersecret"     → unchanged
E-DATA-UNREACHABLE "connect to app:othersecret@db.internal failed; PGPASSWORD=othersecret" → unchanged
```

These aren't this source's password, which F2 covers. They are other secrets that a row, a
`pg_stat_activity.query` or a driver message can carry, and the spec's rule is "No output ever
contains a URL, user password, token or connection string". This should become CF's shared
`scrubCredentials`, with these cases as its tests.

### F7 · P2 · A cancelled call still waits, then runs the Query

`BoundTool.call` returns a bare Promise, and neither the Claude SDK bridge nor the HTTP transport
passes an abort into it. Repro A1 (real MCP HTTP, faked `DataQueries`): the client cancelled at
300 ms. The approval wait was not interrupted (`interrupted: 0`, `finished: 1`), and once it
resolved approved, the Query ran a second time with no caller (`queries: 2`). With the real X this
is a Query logged against a Turn that already moved on. Rows were read for nobody, and the wait
held an HTTP request and a fiber for up to 50 s.

`awaitApproval(approvalId, timeoutMs)` has no `sessionId`, so stopping the session mid-wait can't
end it. Only X's approval machine could, by resolving it to denied. Concurrent calls (A2) each
hold their own wait; whether they share one approval is up to X.

Suggested fix: thread an `AbortSignal` (the MCP SDK's `extra.signal`, and the Claude SDK
handler's) into `call` and interrupt the fiber. Have X resolve open Data approvals as denied when
the session or Turn ends, and pass `sessionId` to `awaitApproval`.

### F8 · P2 · The approval path can overrun Codex's 60 s timeout (PLAUSIBLE)

One call is `credentials()` (N+1 discoveries, F13), then a wait of up to 50 s, then on approval
the Query runs inline under a 30 s statement timeout. If the user approves at 45 s and the Query
takes 20 s, the response lands at about 65 s. Codex has already failed the call, but the Query
ran and is in the Log. The agent retries and gets a second approval or a second run. This is from
reading the code; no slow approval was run live. Suggested fix: measure the deadline from the
call's start. After an approval with less than about 35 s left, return
`{pending:false, approved:true}` with "approved; call again" rather than running inline, or
lower the statement timeout to the time remaining.

### F9 · P2 · One wide cell sets the width for every row

`aligned()` computes column widths over all rows, including the ones the 16k loop drops later. In
repro I3, 199 rows of `[i, "short"]` and one row whose first column is a 3000-element JSON array
(arrays and objects aren't clipped; only strings are) produce:

```
13,976 chars: "                 …(14k spaces)… b (text)\n0 of 200 rows; add a WHERE or an aggregate"
structuredContent.rows: []
```

All 200 rows go, the wide cell's row included. A 20k column name (I2; Postgres caps names at 63
bytes, MySQL aliases at 256) gives `Column headers omitted; select fewer columns.\n0 of 1 rows; add
a WHERE or an aggregate`, while `structuredContent.columns` still carries the 20k name. Live, the
seeded `wide` table put its 3000-element array in the last column. There `trimEnd` hides the
padding, and the text came to 15,944 characters with every row kept.

Suggested fix: clip every rendered cell (JSON included) to the 200-character rule, compute widths
only over the rows being kept, and clip column names too.

### F10 · P2 · Control characters reach the agent, and a newline in a name becomes unqueryable

Only `\r\n\t` are replaced. Live, `line1\nline2\u001b[31mRED\u001b[0m` reached both agents with the
ESC sequences intact; Codex's own reply rendered them as `[31mRED[0m`. Repro I1 keeps `\v`, `\f`,
U+2028 and U+0085 (NEL) as well. Each is a line break or a terminal control in some renderer, so
a row can forge a fake header line, or styling in a Desktop transcript that shows tool output.

Going the other way, the table `"evil\nname"` is listed as `evil name`. Claude concluded it
"can't be selected by name directly". Suggested fix: render C0, C1, U+2028 and U+2029 as visible
escapes (`\n`, `\x1b`, ` `), which keeps identifiers round-trippable, rather than spaces.

### F11 · P3 · Truncation copy

- `1 rows · 34 ms · query …` and `1 data sources in …` (I4).
- With `truncated: true` and `rowCount` equal to the rows returned (the limit cut it, as C's
  `rowCount` allows), the tail says `1 of 1 rows; add a WHERE or an aggregate` (I5). This waits
  on CF's `returned`/`total`.
- When width caused the drop (F9), the hint should be "select fewer columns", not "add a WHERE".
- The checkout prints as an absolute path; the spec's example abbreviates it to `~/code/…`.

### F12 · P3 · Data errors carry the graph's boilerplate

`E-NOT-READY`, `E-INPUT` and `E-SESSION` go through the Constellation `errorResult`, so in a Plain
session the agent reads `Revision: 0` and `Next: Apply these fixes and retry; read status if the
graph changed.`, with `structuredContent {findings, graph: null, revision: 0}`. Live, Claude
quoted the line back. `E-DATA-*` errors use their own `{code, message, fix}`, as the spec says.
Suggested fix: Data rejections should use `failure()`'s shape.

### F13 · P3 · Every call resolves every source, and the reactor is fragile (PLAUSIBLE)

- `credentials()` (`sessions/data.ts:47`) calls `sources.resolve` once per listed source, and each
  resolve re-runs `catalog()`, which means `discover(checkout)`, plus the Keychain for manual
  sources, under D's single semaphore. One `query` against a checkout with 5 sources runs 6
  discoveries and every Keychain read.
- If any one source fails to resolve (a Keychain error on a manual source), `data_sources` fails,
  and so does every `query` on the healthy sources.
- The outside reactor's prefilter matches `\bbun\b|\bnode\b`, so every `bun test` or `bun run …` in
  any session runs list + resolve for every source.
- `store.subscribe` ends the stream silently once the subscriber falls 4,096 items behind, and
  `reactors.ts:79` doesn't resubscribe, so detection stops until the Daemon restarts. A defect in
  the fiber has the same effect, since `Effect.catch` handles failures but not defects.

None of these was triggered live. Suggested fix: one `resolveAll` per call (one discovery);
scrub with whatever resolved and log the rest; resubscribe from the last sequence; drop
`bun`/`node` from the prefilter unless the command also contains `-e`/`--eval`.

### F14 · P3 · Key-name redaction blanks whole columns

`sensitive = /password|passwd|secret|token|credential|connection.?string|database.?url/i` is
tested against the column name, so any column whose name matches is shown as `[redacted]`:
`token_count`, `password_reset_at`, `secret_santa_id`, `credential_type`. Live, that would hide
ordinary columns from an agent debugging auth tables. Suggested fix: redact by value (F2, F6)
rather than by name, or limit name matches to `^(password|passwd|secret|token)$` and `_hash`
columns.

## Against CF's contract (a33bfe23, not yet merged)

The Lead's operator message 398 gave CF's shapes. I read those shapes as described there; I did
not run them. They change the fixes as follows:

- **F2, F6.** Replace `knownCredentials.ts` with `scrubCredentials(text, known)` and
  `scrubDataValue`. Build `known` from D's `resolve().connection.password`, not from the URL.
  Check that `scrubCredentials` handles the encoded, case-folded, query-param and number forms in
  F2 and the patterns in F6. They're the test list.
- **F3.** `scrubCredentials` must not inherit the unbounded URL regex. Clip before scrubbing, or
  bound the scan.
- **F4, F11.** Put `returned` and `total` into the structured output and the tail
  (`200 of 18,402 rows`). With them, the "N of N rows" case (I5) goes away. F4's sentence for
  Claude still needs a field of its own.
- **F9.** `DataValue.Json{text}` arrives as text, so clip it to the 200-character rule like any

- **F7.** Data approvals now go through `RespondToApproval` (`Allow.dataScope`), so an Agent

  them as denied then, and the tool should still interrupt its wait when the MCP request is
  cancelled.
- **F12.** `E-DATA-CANCELLED` exists now. A cancelled MCP call (F7) should log the Query as
  cancelled, not run it.
- **RD/DF locality.** Locality will follow the process that owns the listening socket. A local
  Data Source runs without an approval, so the outside matcher's host comparison (F5) and the
  approval path must use the source's resolved locality, never the hostname in a command.

## What was attacked and held

- **Spoofing session, Turn, URL or path.** `sessionTool` decodes with
  `onExcessProperty: "error"`, so `{source, sql, sessionId}` and similar inputs are `E-INPUT`.
  `data_sources` accepts only `{}`. The session comes from the token's binding, and the checkout
  and current Turn from the EventStore (`sessions/data.ts:17-23`). `source` is resolved only
  within the caller's checkout (D's `catalog(sessionId)`), so a source id from another checkout
  is `E-DATA-UNKNOWN-SOURCE`. M's `data.test.ts` covers this per binding; I re-read it and it
  asserts the outcome.
- **The truncation boundary splitting a secret.** Scrubbing runs before `clip`. The 16k loop drops
  whole rows, and `cappedLines` whole lines, so a known secret or URL is never cut part-way. The
  exact password, its URL and `PGPASSWORD=<known>` were redacted live (notes rows 1–3).
- **Tools on every binding.** Plain, Lead and Worker list `data_sources`, `describe` and `query`
  with `readOnlyHint` (M's HTTP test). Both live Plain sessions found all three.
- **16k and the truncation sentence, for Codex.** `select … from invoices` (300 rows, limit 200):
  11,940 characters ending `200 of 300 rows; add a WHERE or an aggregate`. The `wide` query came
  to 15,944 characters, under the cap.
- **Errors.** `E-DATA-SQL` reached both agents as `{code, message, fix}` with `isError`.
- **The outside detector's cost and placement.** It runs as a separate scoped subscriber, and its
  `filter` is a synchronous tag check, so it isn't in the decide/commit/ack path and can't block a
  command. The tokenizer is linear: a 1 MB `node -e …` takes 39 ms, a 400k `psql a=b …` 56 ms, and
  200k quotes 3 ms. Declined commands are skipped. (This holds once F1 is fixed; today it never
  runs.)
- **Approval outcomes.** Approval runs the call again within the same call. A second
  `DataApprovalRequired` returns pending without a second wait. Denial returns `E-DATA-DENIED`
  with the user's reason. These were checked with fakes in M's tests and in A1/A2.
- **The merge `075b52e3`.** The conflict in `data/index.ts` keeps D's `resolve` (now returning
  `connection`) and M's `awaitApproval`/`recordOutside`. The adapted fakes only add `connection`.
  `bun test src/mcp src/data` → 149 pass, 1 skip, 0 fail. The `connection.password` D added is
  exactly what F2's fix needs.

Not attacked: live `describe` (still unsupported in both the stub and the review harness), real
Data Source approvals and the Query Log (X), MySQL, and the Desktop's rendering of tool output.
Live `reachable: false` for a reachable database is D's probe, noted here for D.
