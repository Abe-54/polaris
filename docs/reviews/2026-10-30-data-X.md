# Adversarial review: X, read-only execution, Query Log and Data Source Approvals (ENG-644)

Reviewed: `43336ee6` (merged in `d2033702` on the integration branch), diffed against `d2033702^1`.
Read against ADR 0091, `docs/specs/data-tools-v1.md` and `docs/research/data-bun-sql.md`, with
RU2 F13 (`docs/reviews/2026-10-30-data-U2.md` at `c0b2de8a`) and RU3 F3, F7 and F10
(`docs/reviews/2026-10-30-data-U3.md` at `688086fa`) folded in as the Lead asked. Reviewer: RX,
Opus 5.5, 2026-10-30. No product code changed.

Every SQL probe ran through X's real `executeRead` or the production Data composition
(`dataServices` + `data.query.stream`), against the Lead's disposable Postgres 16
(`127.0.0.1:55432/ledger`) and MySQL 8.4 (`127.0.0.1:53306/ledger`,
`--log-bin-trust-function-creators=1`) on this Host, with Bun 1.4.4. Probe sources are in
`docs/reviews/2026-10-30-data-X/` (`.ts.txt`). Credentials are replaced by `RX_PG_URL`,
`RX_MYSQL_URL` and `RX_PASSWORD`. To rerun one, copy it into `apps/daemon/src/data/` without
`.txt`.

**Verdict.** The read-only boundary held for every direct write. No probe committed a write through
X's own connection on either engine. Multi-statement input, `COMMIT`/`ROLLBACK` smuggling, `;`
hidden in comments and quotes (including RU2 F13's filter through `data.query.stream`), writable
CTEs, `FOR UPDATE`, `DO`, `COPY`, `LISTEN`/`NOTIFY`, `PREPARE`, `SET TRANSACTION`, `/*!`, `/*+`,
`OUTFILE` and write functions were all refused. Timeouts, `KILL QUERY` and pool release are
correct.

Three P1s remain:

- **F1:** the approval store can make a Remote target readable with no approval.
- **F2:** `READ ONLY` doesn't stop side-effecting functions, and with `dblink` installed a write
  committed.
- **F3:** the row cap doesn't bound memory: one 100 MB cell costs the Daemon ~590 MiB.

F4 to F9 are P2s: session state outliving the transaction, approval-scope semantics, the
two-session card (RU3 F3), error positions (RU3 F7), and spec coverage that misses F1 and F7.

### F1 · P1 · A Local source's write-policy change grants Remote reads of the same target

`DataSourceAccess.live.change` writes one rule row keyed by
`targetKey = [engine, host, port, database, user]`. It stores `revoke ? "needs-approval" :
current.access`, and `current.access` for a Local source is the default `"read"`
(`approvalStore.ts:117-122`). `read` then returns that exact row ahead of any locality check, and
`require` returns early on `access === "read"` (`approvals.ts:84`). Nothing records that `"read"`
was a Local default rather than a decision.

Failing scenario (probe A1, real `DataApprovals` layer with the Session machine):

1. A Local source `postgres localhost:5432/app as reader`: `require` runs it, no approval.
2. The user changes its writes to `off` in Data (`data.source.access {writes: "off"}`
   → `sources.access` → `access.change`).
3. The same target resolves Remote: the compose proxy stopped and an SSH tunnel to production
   now listens on `localhost:5432`, exactly the case ADR 0091 says must be Remote. `require` →
   **runs, no approval asked**.
4. Control: the same Remote source with a different database name → `approval requested`.

Suggested fix: store only user decisions (`approved`, `denied`, `needs-approval` after revoke) and
keep writes policy in its own column or table. Compute `read` from locality at read time, never
from a stored row. Add a model-test action for "change writes on a Local source, then flip
locality".

### F2 · P1 · READ ONLY doesn't stop side-effecting functions (RU3 F10)

The guard is lexical and Postgres has no function check. The database's read-only transaction
refuses writes to its own relations and sequences, but not the effects below. All ran through
`executeRead` as `postgres`/`root` (the URL's user):

| Engine | Statement | Result |
|---|---|---|
| Postgres | `SELECT pg_terminate_backend(<pid of another client>)` | `true`: the backend was terminated (the victim pool silently reconnected) |
| Postgres | `SELECT pg_reload_conf()` | `true` |
| Postgres | `SELECT pg_read_file('/etc/hostname')`, `pg_ls_dir('/')` | the server's files. MySQL's `LOAD_FILE` is refused, so the two engines disagree |
| Postgres | `SELECT pg_notify('rx_channel','hello')` | ok, delivered at commit |
| Postgres | `SELECT pg_advisory_lock(…)` | ok, and held after the Query (F4) |
| Postgres | `SELECT txid_current()` | ok (assigns an xid) |
| Postgres | `SELECT dblink_exec('dbname=ledger', 'UPDATE rx_probe SET v=5')` with `dblink` installed | **`UPDATE 1`, committed: the sentinel row read `v = 5` afterwards** |
| MySQL | `SELECT GET_LOCK('rx_lock', 0)` | `1`, and held after the Query (F4) |
| MySQL | `SELECT BENCHMARK(1000, MD5('x'))`, `SLEEP(n)` | ok (CPU and time, bounded by the 30 s timeout) |

`dblink` and `postgres_fdw` are available but not installed by default here, and installing them
needs a write. On a target where either is installed, the read path is a write path. The function
in `dblink_exec` opens its own connection outside the read-only transaction. A user-defined
`SECURITY DEFINER` function that calls `dblink` or a foreign table does the same.

Refused, as they should be: `nextval`, `setval`, `lo_import`, `lo_export` (no object),
`set_config('transaction_read_only','off',true)`, and write functions on both engines
(`E-DATA-READ-ONLY`).

Suggested fix: two layers.

1. **Restricted role (the real boundary).** ADR 0091 already names a SELECT-only database user per
   Data Source as the hardening. Make it the documented default, and warn in Data when the
   connecting user is a superuser or has `pg_signal_backend`, `pg_read_server_files`, `EXECUTE` on
   `dblink*`, or MySQL `SUPER`/`FILE`.
2. **Function deny-list (second guard).** Refuse, outside literals and comments, calls to
   `pg_terminate_backend`, `pg_cancel_backend`, `pg_reload_conf`, `pg_rotate_logfile`,
   `pg_read_*file`, `pg_ls_*`, `pg_stat_file`, `lo_*`, `dblink*`, `pg_notify`,
   `pg_advisory_*`/`pg_try_advisory_*`, `set_config`, `txid_current`/`pg_current_xact_id`, and
   MySQL `GET_LOCK`, `RELEASE_*LOCK`, `BENCHMARK`. As with the MySQL allowlist, a lexical list
   stays incomplete (user-defined functions, `SECURITY DEFINER`), so it can't replace the role.

### F3 · P1 · The row cap doesn't bound memory

`boundedRead` fetches `limit + 1` rows and decodes all of them before anything is clipped. A 17 MiB
cell becomes a `Truncated` preview in `fitRow`, but only after the driver has received it, decoded
it and kept it in the decoded rows. The agent path then keeps 16,000 JSON bytes (`queries.ts:104`),
yet the Daemon already holds the whole result. Peak RSS of one read in a fresh process
(probe `rx.memory.probe.ts`):

| Engine | Query | Limit | Rows returned | Peak RSS over baseline |
|---|---|---|---|---|
| Postgres | `generate_series(1,1000000)`, 1 KB text per row | 10,000 | 10,000 (22 chunks, 10.1 MB on the wire) | +113 MiB |
| Postgres | one 17 MiB cell | 200 | 1 (`Truncated`) | +101 MiB |
| Postgres | **one 100 MiB cell** | 200 | 1 (`Truncated`, 11 KB on the wire) | **+587 MiB** |
| Postgres | **20 rows × 10 MiB** | 200 | 20 | **+803 MiB** |
| MySQL | 100,000 rows, 1 KB text per row | 10,000 | 10,000 (22 chunks) | +144 MiB |
| MySQL | one 17 MiB cell | 200 | 1 (`Truncated`) | +95 MiB |
| MySQL | one 100 MiB cell | 200 | `NULL` (over `max_allowed_packet`) | +0 MiB |
| MySQL | **20 rows × 10 MiB** | 200 | 20 | **+551 MiB** |

Each pool allows two concurrent Queries and there can be 16 pools, so a few agents sampling a wide
table can push a Raspberry Pi 4 Daemon out of memory. The 1M-row cap itself holds: the cursor
(Postgres) and the `LIMIT` wrapper (MySQL) stop at `limit + 1` rows.

Suggested fix: a byte budget alongside the row cap. On Postgres, wrap selected columns with
`left(col::text, N)`, or fetch in small `FETCH FORWARD` batches and stop when bytes exceed the
budget. On MySQL, lower the session `max_allowed_packet` for the read, or stream rows and abort
when over budget. Disclose the per-cell receive-before-clip limit until then (W shares it for
previews).

### F4 · P2 · Session state outlives the read-only transaction on pooled connections

`connection.begin("read only", …)` ends the transaction, but session-level state stays on the
pooled connection, which is shared by every Agent Session and the Desktop for that source (the pool
is keyed by connection options, not by session). Probe `rx.effects.probe.test.ts`:

- `SELECT pg_advisory_lock(777)` returned. Another client's `pg_try_advisory_lock(777)` returned
  `false` at +0 s and +3 s, and `true` only at +7 s, after the pool's 5 s idle close. MySQL
  `GET_LOCK('rx_lock2',0)` behaved the same: held by the pool's thread at +0 s and +3 s, free
  at +7 s. While the pool stays busy, the lock is held indefinitely.
- `SELECT set_config('search_path','pg_catalog',false)` changed the session. The next Queries on
  that pool alternated between `"$user", public` and `pg_catalog`, depending on which of the two
  connections they got. A later Query from another session can resolve unqualified names
  differently. `statement_timeout` held, because `configure` sets it `LOCAL` each time.
- MySQL `SELECT @rx_v := 5`: later Queries on the same connection read `@rx_v = 5`.

Suggested fix: reset on release. On Postgres, `DISCARD ALL` (or `RESET ALL` plus
`SELECT pg_advisory_unlock_all()`). On MySQL, `COM_RESET_CONNECTION` or `RELEASE_ALL_LOCKS()` plus
clearing user variables. Alternatively, close the connection after any Query that touched a deny-list
function. This also covers W's write path through the shared `executeTransaction`.

### F5 · P2 · `Allow { remember: false }` is remembered

`ApprovalStore.apply` handles `Allow` without reading `choice.remember`: it always writes the exact
rule `approved`. Probe A2: after `Allow { remember: false }`, the next `require` on the target runs
without asking. The spec says approvals "are remembered per Host", so remembering may be intended.
But `remember` is on the wire, and the spec keeps "the normal approve grants for Extensions and
Linked Devices". An Extension or the G2 that sends `remember: false` to mean "once" grants it
permanently. Lead call: honour `remember: false` as a one-request grant, or refuse it for Data
approvals with a clear error.

### F6 · P2 · Server scope covers every user, and target revoke doesn't remove it

`serverKey = [engine, host, port]`. Probe A3: after a server-scope `Allow` for
`db.example:5432/app as reader`, a source for `postgres/postgres` on the same server ran with no
approval. Revoking the approved target re-gated only that target; the other database stayed
approved. The spec does say "the whole server", so the scope is as written, but:

- it includes **other users**, so other credentials on the same server, possibly with more
  privileges (F2), are approved too;
- `data.source.access {revoke}` can never remove a server grant, so a user who granted the whole
  server can't take it back from any source's card.

Suggested fix: include `user` in the server key (whole server for this user), and make revoke
clear the server rule when the target's access came from it.

### F7 · P2 · Two sessions pending on one target (RU3 F3)

`require` looks for an existing request only in `record.pending` of the calling session
(`approvals.ts:107-115`). Two Agent Sessions reading the same Remote target open two cards. When the
user answers one, `apply` sets the rule for the target, but the other request stays `pending`
in its session (`awaitApproval` keeps waiting until its timeout, and the card stays until its Turn
ends). A retry in that session succeeds, because the rule now allows it. Suggested fix: on `Allow`
or `Deny` for a target, resolve every other pending Data request for the same `targetKey` (or
`serverKey` for a server grant) through the Session machine, as `ApprovalResolved` with the
same decision and `resolvedBy: "same-target"`.

### F8 · P2 · Error positions (RU3 F7)

The spec's `E-DATA-SQL` row promises "the scrubbed database message and position". Probe
`rx.pos.probe.ts`:

- Postgres `SELECT 1 FROMM x` → `syntax error at or near "x"` with no position: `queryError`
  reads only `message`, and Bun's `position` is dropped.
- MySQL `SELECT 1 FROMM x` → `… near 'x\n) AS polaris_capped LIMIT 201' at line 2`. The user
  sees X's wrapper and a line number off by one.

Suggested fix: on Postgres, take `position` and subtract the length of
`DECLARE polaris_data NO SCROLL CURSOR FOR\n`. On MySQL, strip the `\n) AS polaris_capped LIMIT n`
suffix from the near-text and subtract one from the line.

### F9 · P2 · The spec and model test miss F1 and F7

`module data_approvals` models a single session over three Remote targets. It has:

- no locality and no write-policy change, so F1 can't occur in it;
- no second session, so F7 can't occur in it;
- no Turn-end withdraw (`restart` stands in for every ending);
- `waitExpired` as a no-op.

Its two non-trivial safety clauses, `denied ⇒ ¬allowed` and `revoked ⇒ ¬allowed`, follow from the
definition of `allowed`, so they can't fail. `dataApprovals.model.test.ts` likewise generates only
Remote sources and never calls `change` with `writes`. The real-machine withdrawal on
`harness.turnEnded`, `turn.interruptUnattended`, `session.fail` and `daemon.recover` is covered,
and passes, in `approvals.test.ts`, not in the spec.

Suggested invariant: `reads` only for targets that are Local or have a user `Allow` since their
last revoke, with locality as nondeterministic state and a `changeWrites(t)` action, plus a
two-session variant for F7.

### F10 · P3 · Queue wait isn't bounded by the Query's timeout

The timer starts after `lease.sql.reserve({ signal })`. Probe T4: with two 3 s sleeps holding the
pool, a third Query waited, and an abort at 500 ms cancelled it in 502 ms. So cancellation works,
but without an abort a queued Query waits for the holders and then gets its own full 30 s. W keeps
this behaviour in the shared `executeTransaction`. Suggested fix: start the deadline before
`reserve()`.

### F11 · P3 · Query Log retention

`put` keeps the newest 10,000 entries per checkout. There is no age bound and no bound across
checkouts. `sql` and `command` keep up to 32,000 characters each, so one checkout's log can reach
~320 MB of `data.sqlite`. Suggested fix: an age bound (for example 30 days) and a byte bound per
checkout.

### F12 · P3 · Revoking a Local source makes it ask

`change(source, undefined, true)` stores `needs-approval` for any target, so after a revoke a Local
source asks for approval. If that is intended, say so in the spec. If not, F1's fix (stop storing
the Local default) removes it.

### F13 · P3 · MySQL shared locking reads

`SELECT … FOR SHARE` and `LOCK IN SHARE MODE` are allowed by S's matrix and run (probe: `ok`),
taking shared row locks that block writers until the read-only transaction ends, for up to 30 s.
Postgres refuses both in a read-only transaction. Suggested fix: refuse them on MySQL too, for
parity, or document them.

## What was attacked and held

**Read-only escapes** (probe `rx.probe.test.ts`; sentinel row `v = 0` before and after on both
engines, sequence `is_called = false`):

| Postgres | MySQL |
|---|---|
| `SELECT 1; UPDATE…`, `COMMIT; UPDATE…`, `ROLLBACK; UPDATE…` → `E-DATA-READ-ONLY` | same, plus `SET autocommit=1`, `SET TRANSACTION READ WRITE` → `E-DATA-READ-ONLY` |
| `/* ; */`, nested `/* /* */ ; … */` (one comment on Postgres) → runs only `SELECT 1` | nested `/* /* */ ; UPDATE … */` (not nested on MySQL) → refused |
| `-- ;\n; UPDATE` → refused | `# ;\n; UPDATE`, `--;\nUPDATE` → refused; `--\t;\nUPDATE` → a comment, then a syntax error |
| `E'\'; UPDATE…; --'` and `$$…$$` → one literal | `'\'; UPDATE…'` and `"a\"; UPDATE…"` → one literal |
| `SET TRANSACTION READ WRITE`, `SET SESSION CHARACTERISTICS`, `COPY … TO PROGRAM`, `COPY … FROM STDIN`, `LISTEN`, `NOTIFY`, `DO $$…$$`, `PREPARE`, `EXECUTE` → syntax errors inside the `DECLARE … CURSOR FOR` wrapper | `/*!50000 …*/`, `/*+ SET_VAR(…) */`, `LOAD_FILE`, `INTO OUTFILE`, `DO`, `HANDLER` → refused; `INTO @var` → `Misplaced INTO` |
| writable CTE → `DECLARE CURSOR must not contain data-modifying statements` | `FOR UPDATE`, a `MODIFIES SQL DATA` function → `E-DATA-READ-ONLY` |
| `FOR UPDATE`, `FOR SHARE`, `nextval`, `setval`, `lo_import`, a plpgsql `UPDATE` function → `E-DATA-READ-ONLY` | `SELECT 1) AS a UNION ALL (SELECT 2` (wrapper break-out) → syntax error |
| `set_config('transaction_read_only','off',true)` → refused by Postgres | |

**RU2 F13 through `data.query.stream`** (probe `rx.stream.probe.ts`: the production composition,
the Desktop's own `tableSql`, a saved source with its password in Secure Storage). These were
refused with `E-DATA-READ-ONLY` before the user SQL reached the server, on both engines:

- the Table tab filters `false; commit; insert …; select 1 as id`, `id = 1; insert …`,
  `id = 1 /* ; */ ; insert …`, `id = 1 -- ;\n; insert …`, Postgres
  `id = 1 /* /* */ ; */ ; insert …` and MySQL `id = 1 # c\n; insert …`;
- the SQL tab's `select 1; insert …`, `commit; insert …` and `select 1 /* hide ; */; insert …`.

Only `configure`'s own statements ran before the guard. `rx_events` held only id 1 afterwards on
both engines. `v = 'x;y'` ran. `id = 1 --` commented out the Table tab's `ORDER BY`/`LIMIT`, and the
Daemon's cap still applied.

**Timeouts and cancellation** (probe `rx.timeout.probe.test.ts`):

- `pg_sleep(40)` → `E-DATA-TIMEOUT` at 30,030 ms; MySQL `SLEEP(40)` → at 30,010 ms. No sleep was
  left in `pg_stat_activity` or `PROCESSLIST`, and the next Query ran in 42 ms and 2 ms.
- MySQL: with A = `SLEEP(10)` and B = `SLEEP(3)` on one pool, cancelling A removed only A's
  thread from `PROCESSLIST`. B kept running and completed in 3,014 ms; A → `E-DATA-CANCELLED` in
  802 ms. `KILL QUERY` reached the right thread, and the reservation was held until the kill
  settled. Postgres: A cancelled in 815 ms, B completed in 3,072 ms.
- 20 Queries aborted at 50 to 130 ms: connections peaked at pool + control (5 and 6, over a
  baseline of 3), a Query right after ran in 2 ms, and after 6.5 s idle both pools were back to
  baseline. Nothing leaked.

**Idle cost.** Pools are lazy and close 5 s after their last Query (above). The approval
projection is commit-driven, with no timer. `bun run bench idle --quick --compare
packages/bench/baselines/mac14-13-apple-m2-max-12c-m31-idle-quick.json` → "no regressions beyond
tolerance": 7.2 wakeups/s with no Client against a 10.5 baseline, footprint 63 MiB against 97.
The run started with 10.1 cores busy, so its CPU figures aren't comparable.

**Query Log:**

- In the stream probe's 22 entries, the password appears nowhere: the SQL tab's literal password
  was stored as `'[redacted]'`.
- Desktop Queries are `author.kind = "user"`. Agent Queries take `sessionId` and Turn from the
  authenticated MCP binding (`mcp/sessions/data.ts`), never from tool arguments.
- Remote parameters aren't stored (`services.testing.ts` asserts it).
- `recordOutside` is idempotent: `INSERT OR IGNORE` on `outside:<session>:<item>`, also asserted.

**Approvals:**

- A target changed under the same name needs a new approval: the key excludes the name. A grant
  for server A doesn't cover server B.
- A deny is remembered for every session until revoke (probe A4).
- A refresh between check and run can't swap the target: `resolveReadSource` refreshes, then
  `require` and `readEffect` use the same resolved snapshot.
- Requests go only through `decideSession(… "data.approvalRequested")`, and no
  `data.approval.decide` RPC remains (grep).
- Turn end, unattended interrupt, session failure and Daemon recovery withdraw pending requests as
  denied (`approvals.test.ts`, passing).

**Spec and model-based tests.** `bun run spec` exited 0: "Data approval scenarios" and "Data
approval safety" pass, and the expected finding mutants still violate.
`bun test apps/daemon/src/verification` → 32 pass, 0 fail, 47,039 assertions (26.4 s). As F9 says,
these runs pass without covering F1 or F7.
