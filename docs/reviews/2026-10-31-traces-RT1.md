## Findings

### 1. P0: realistic secrets reach traces.sqlite unredacted (CONFIRMED)

`apps/daemon/src/traces/redact.ts:6` (key regex), `redact.ts:11` (`redactText`), `redact.ts:36` (bytes passed through as-is), and `packages/protocol/src/dataValues.ts:82` (`scrubCredentials`).

Repro: `redaction.test.ts`, 10 failing cases. Each case posts through the real receiver, flushes, then searches the raw `traces.sqlite` bytes for the secret.

- **SQL without `=`**: `ALTER USER app WITH PASSWORD 'x'` and `CREATE USER app IDENTIFIED BY 'x'`. The value regexes need `key[:=]`.
- **CLI flags**: `process.command_line` = `node server.js --password x`.
  - Also `process.command_args` = `["--token","x"]`. The default Node resource detector collects this, so every Node app sends it.
- **Env-style assignments whose key does not end with the keyword**: `AWS_SECRET_ACCESS_KEY=x`. The regexes need the key to end in `secret`, `token` and so on.
- **Bare vendor tokens with no label**: `sk-ant-api03-…`. `ghp_…` and JWTs are also missed (seen in the probe).
- **Header and attribute keys the key regex misses**: `http.request.header.x-auth`, `*.signature`. The probe also showed `jwt`, `session_id`, `passphrase` and `pwd` stored in clear.
- **Span status message** with a SQL password (`redactText` is partial and misses the same patterns).
- **`bytesValue`**: base64 of `password=x` is stored untouched.

Smallest fix:
1. Add these value patterns to `redactText`:
   - `PASSWORD\s+'…'` and `IDENTIFIED BY\s+'…'`;
   - `--(password|token|secret|api-key)[= ]\S+`;
   - `[A-Z0-9_]*(SECRET|TOKEN|PASSWORD|API_KEY)[A-Z0-9_]*=`;
   - well-known token prefixes (`sk-`, `ghp_`, `gho_`, `xox[abp]-`, `AKIA`, `eyJ…\.…\.…`).
2. Run the array items of `process.command_args` as one joined command line, so a flag can redact the value after it.
3. Add `auth`, `signature`, `jwt`, `session`, `passphrase` and `pwd` to `sensitive`.
4. Redact the decoded `bytesValue`, or drop it.

Regression tests: the cases in `redaction.test.ts`.

### 2. P1: any URL makes the value "[redacted]" (CONFIRMED; reported by P7, widened here)

`redact.ts:28` swaps the whole value when `redactText` changes anything. `scrubUrls` (`dataValues.ts:13`, called from `scrubCredentials`) replaces every URL with `[redacted URL]`, not only URLs that carry credentials:

- `bun -e '…redactText("https://example.com/orders")'` prints `[redacted URL]`.
- `at file:///tmp/a/server.mjs:7:34` becomes `at [redacted URL]`.

As a result, `url.full`, `http.url`, `server.address` URLs and every ESM `exception.stacktrace` are stored as `"[redacted]"`. Span names that contain a URL are partly replaced. This defeats the Traces mode's route and URL display and the in-project frame lookup that traces-tools-v1 promises.

Repro: `redaction.test.ts`, "credential-free … survives redaction" (3 cases).

Smallest fix: don't use `scrubCredentials` for trace values. Write a trace-specific URL scrub that removes only the userinfo and the values of sensitive query parameters (`token`, `sig`, `signature`, `code`, `key`, `X-Amz-*`, `access_token`, `password`), and leaves the scheme, host, path and other parameters intact.

### 3. P1: closing a Harness scope revokes an active session's endpoint (CONFIRMED)

`apps/daemon/src/traces/environment.ts:28` adds `revokeSession` as a finalizer on the Harness scope. That scope closes:

- on dormancy, after 30 minutes idle (`engine/runtime.ts:274` `goDormant`, which emits `stopHarness`);
- on every graceful Daemon shutdown and upgrade (`engine/Engine.ts:188-190` stops every live Harness).

So:
- the README's "Existing endpoints survive a Daemon restart" holds only after a crash;
- a dev server or background process the agent started keeps its old token and gets 401 for the rest of its life;
- the next Harness gets a new token, because `endpoints` loses the entry when the token is revoked.

Repro: `receiver.test.ts`, "closing a Harness scope … keeps an active session's endpoint". The session is still active, but the post is refused: expected 200, received 401.

Smallest fix: revoke on session end (archived, failed or deleted, which `authenticate` already checks lazily), not when the Harness scope closes. If the token must still rotate, keep the old hash valid while the session stays active.

### 4. P1: error Spans are never pruned by age or size (CONFIRMED)

`apps/daemon/src/traces/retention.ts:23`: `droppableSpan = status<>'error' AND unpinned`. Error Spans and the logs attached to them are excluded from both pressure and age pruning, with no hard cap. An app stuck in a failure loop that emits error Spans grows `traces.sqlite` without limit. The database shares a disk with the event store, and on a Pi that disk is small.

Repro: `retention.test.ts`.
- Setup: a 20 kB budget and a one-day age limit; 500 error Spans that are 31 days old.
- Result: 642,000 bytes retained; the assertion allows at most 80,000.

Smallest fix: keep the error-Span exception only within a hard ceiling, for example 2× `maxBytes`, and prune the oldest error Spans first once over it. Always drop error Spans past `maxAge` unless their Trace is pinned.

### 5. P2: any local process, with no token, can keep every exporter at 429 (CONFIRMED)

`apps/daemon/src/traces/receiver.ts:106`: the two-slot `inFlight` limit is taken before Host, path or token checks. Every refusal path (`receiver.ts:116-128`) then reads the body to keep the connection alive. A process with no token, or another user on the same Linux host, can hold both slots:
- send `POST /anything` with `Content-Length: 1000` and never finish the body;
- Bun closes each such request after about 10-12 s (`idleTimeout: 10`);
- reconnecting at once keeps both slots taken.

Every valid exporter is then refused with 429 for as long as the attacker keeps going. One noisy checkout can starve the others in the same way, because the slots, the 32-message queue and the 16 MiB pending cap are all shared across checkouts.

Repro: `receiver.test.ts`, "an unauthenticated local process holding two slow bodies…". A valid post 15 s in gets 429 (expected 200).

Smallest fix:
1. Validate Host, Origin, path and token before taking a slot.
2. Answer refusals with `connection: close` instead of draining up to 4 MiB.
3. Give each request a total body deadline, for example 5 s.
4. Optionally, give each token its own slot.

### 6. P2: storage failures answer HTTP 400 and wedge the worker (CONFIRMED)

`apps/daemon/src/traces/worker.ts:181` maps anything that is not an `IngestError`, such as the `storageError()` `TraceError` or an open failure, to status 400. OTLP/HTTP exporters treat 400 as permanent and drop the batch.

Also, `worker.ts:74` sets `failed = true` after one failed flush. That worker refuses everything until it retires after 30 s with no requests, and a steady exporter or a watching client never lets that happen. The failed flush also drops the pending batches of every checkout.

Repro: `receiver.test.ts`, "a storage failure answers a retryable status, not 400". With the database path made unusable, the post returns 400.

Smallest fix:
1. Map `TraceError` and other non-`IngestError` failures to 503.
2. Clear `failed` on the next successful `database()` probe, or respawn the worker once after a failure, instead of waiting for quiet.

### 7. P2: the receiver never binds again after a port conflict (CONFIRMED)

`apps/daemon/src/traces/receiver.ts:164` calls `Bun.serve` once. After `EADDRINUSE`, availability stays `Unavailable` until the Daemon restarts, even once the other process has exited. A short-lived dev collector or a second test Daemon therefore disables Traces for the whole uptime.

Repro: `receiver.test.ts`, "the receiver binds once the port is freed after a conflict". The port is free for 3 s and availability is still `Unavailable`.

Smallest fix: retry the bind with backoff while `Unavailable`, for example every 30 s, or each time a session asks for `setup` or `environment`. Report the result through `setAvailability`.

### 8. P2: memory after trace bursts is allocator retention the Daemon never releases (CONFIRMED, measured)

Experiment: `/tmp/rt1/bursts.ts`, not committed. Six bursts of 50,000 Spans went through the real receiver and worker (`withTraceFixture`, `quietMs: 2000`). After each burst the worker retired, then I measured RSS and the main-thread JSC heap (`bun:jsc heapStats`).

| | RSS MiB | Main JS heap MiB |
|---|---:|---:|
| Start | 65.0 | 14.9 |
| Flushed, range across bursts | 95–165 | 13.6–18.5 |
| Worker retired, range | 81–103 | 13.6–18.5 |
| After `Bun.gc(true)` | 76–91 | 12.4–14.4 |
| After `Bun.shrink()` | 72–79 | 11.4 |

What the measurements show:
- **Not held by the main thread**: the main-thread heap returns to about 11–14 MiB after every burst, so nothing there (watch snapshots, pending maps, admission buffers) holds the memory.
- **No growth across bursts**: RSS after retirement stays flat over all six bursts (burst 6 is lower than burst 2).
- **Retained, and not released by the Daemon**: what remains is retained by the allocator, from the retired worker and the main allocator. `Bun.gc` plus `Bun.shrink` gives back most of it.
  - The Daemon never runs that release after trace work. `releaseWhenQuiet` (`apps/daemon/src/memory/release.ts:44`) fires only on `TurnEnded`.
  - So the BENCH.md post-quiet figure of 108–268 MiB stays until the next Turn ends.

I did not rerun the full 200k-Span `bench traces --profile`; this in-process experiment answers the main-thread versus allocator question more directly.

Smallest fix: run `releaseMemory` after the worker retires, from a `TraceWorkerClient.stop` callback. Record the before and after in BENCH.md.

### 9. P3: trace-tokens.json grows by one hash per binding per restart (CONFIRMED)

`apps/daemon/src/traces/tokens.ts:32` and `tokens.ts:58`: the raw tokens in `endpoints` live only in memory, so after a restart `issue()` saves a new hash for the same binding. Old Workspace and terminal hashes are never removed: `revokeWorkspace` has no caller, and lazy revocation needs a request that never comes. The `exported` map also grows by one entry per session, forever.

Repro: `receiver.test.ts`, "trace-tokens.json does not gain a hash per Daemon restart…". Five vault instances for one binding leave five hashes.

Smallest fix:
1. Keep one hash per binding: replace the old hash when issuing a new one.
2. Call `revokeWorkspace` when a Workspace is removed.
3. Prune `exported` entries for archived sessions.

### 10. P2: each request re-reads all Turns while a Turn is active (PLAUSIBLE)

`apps/daemon/src/traces/sessions.ts:59-63`: the context cache is keyed on the `SessionRecord`'s identity, which changes with every event of a working session. Each OTLP request during a Turn therefore runs `readTurns({limit: null})` on the main thread. For a session with thousands of Turns that is a full read per request, up to two at a time.

Not reproduced: I did not build a long-history session under load. This is inferred from the code.

Smallest fix: cache the Turn intervals by session id and append or update the last interval from the events, or key the cache on the Turn count plus the last Turn's `endedAt`.

### 11. P2: a session in a subfolder and that Workspace's terminals use different checkout keys (PLAUSIBLE)

- A session's checkout is `realpath(session.cwd)` (`sessions.ts:60`).
- A terminal's checkout is the containing Workspace or worktree root (`sessions.ts` `workspace()`).

If a session's cwd is a subfolder of its Workspace (a monorepo package), Traces from that Workspace's terminals are stored under the root and never appear in that session's Traces view. Not reproduced: I did not confirm whether the Desktop App can start a session in a subfolder.

Smallest fix: key sessions by the same containing root that `workspace()` resolves.

### 12. P3: every traces.watch page carries the raw endpoint token (CONFIRMED by code)

`apps/daemon/src/traces/runtime.ts:145` returns `http://127.0.0.1:4319/otlp/<token>` in each `TracesSnapshot`, and `rpcs.ts` attaches it to every page. The token can only write telemetry into one checkout, never read it. Clients are trusted and the Desktop App shows the endpoint on purpose, so the impact is low. Still, it now lives in renderer state and in any log of snapshots.

Smallest fix: send the endpoint only on the first page, or behind an explicit "copy endpoint" call.

### 13. P3: each record is serialised twice per ingest (CONFIRMED by code)

`decoder.ts` (`append`) and `worker.ts:124` both call `JSON.stringify` on every record to count its bytes, and `writeBatch` calls it a third time. That is extra CPU per Span on a Pi.

Smallest fix: return the byte count from `decodeBatch` and reuse the serialised value in `writeBatch`.

## Attacked with no finding

- **Origin and Host**, with raw sockets against the real receiver (`/tmp/rt1/origin.ts`):
  - `Origin: null` and same-host `Origin` → 403;
  - `Host: evil.test:4319` (DNS rebinding) → 403;
  - `Host: localhost:4319` → 200, which is intended;
  - an absolute-form target with an evil host but a loopback Host header → 200. That is not reachable from a browser.
- **Binding**: IPv6 `::1:4319` refuses connections, because the receiver binds `127.0.0.1` only. No non-loopback bind.
- **Compression**: `Content-Encoding: gzip` → 415.
- **Malformed and deep protobuf**: nesting 20,000 and 200,000 levels deep (3.2 MiB) throws a `RangeError` inside protobufjs before `bounded()`. The worker catches it and answers 400; nothing crashes or hangs. A depth of 1,000 is refused as "exceeds 32 levels".
  - Truncated protobuf and deep JSON are covered by T1's own tests.
- **Body size limits**: the 4 MiB body limit, the 10,000-record limit and the 16 MiB expanded-record limit are enforced in `decoder.ts`. Resource amplification is bounded (T1's test).
- **Cross-checkout reads**: every query and the span upsert key include `checkout`, and the RPCs resolve the checkout from a session. Session A's token binds A's canonical checkout, and `authenticate` re-checks it against the event store.
- **Token storage**: `trace-tokens.json` holds hashes only (mode 0600). No token appears in errors, the receiver logs nothing, and archived, failed or removed sessions and Workspaces are refused and revoked lazily.
- **Turn attribution**: a Span is attributed to the Turn whose interval contains its start time, a Span between Turns gets `null`, and `launchedTurn` is always `null` (documented, ENG-673). Recovery marks interrupted Turns ended, so no stale open interval absorbs later Spans. Clock skew is not a factor because the sender is on the same Host.
- **Env injection**:
  - a user-set `OTEL_EXPORTER_OTLP_ENDPOINT` or `…TRACES_ENDPOINT` suppresses injection for Claude, Codex and terminals;
  - the injected endpoint has no trailing slash;
  - Codex's `shell_environment_policy.set` is applied after Codex's own filtering;
  - the reviewer allowlist passes only endpoint variables.
  - Remaining edge, P3 and not filed separately: an empty-string user variable also suppresses injection, and a user who sets only `…LOGS_ENDPOINT` still has metrics sent to Polaris, which answers 404.
- **Worker lifecycle**: lazy spawn; quiet retirement flushes; Daemon shutdown flushes through `close()`; a worker crash loses only the acknowledged pending window (documented).
- **Build**: `bun scripts/build-daemon.ts darwin-arm64` fails identically on `origin/main` (`ae37cd2d7`, a fresh worktree after `bun install --frozen-lockfile`) and on `08798fa8f`, unable to resolve `@ast-grep/napi-linux-arm64-{musl,gnu}` from `rules/patterns/native.ts:38-39`. This failure was already present on main; T1 did not cause it.
