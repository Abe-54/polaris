# Adversarial review: C, Data contracts and service stubs (ENG-644)

Reviewed: `25e5a7f9` (merged in `b5aec789` on `polaris/grill-with-docs-i-want-to-do-7ce3`), diffed
against `8021296c`. Read against ADR 0091, `docs/specs/data-tools-v1.md`, CONTEXT.md → Data and
DESIGN.md → Data. Reviewer: RC, Opus 5.5, 2026-10-30. No product code changed.

**Verdict.** The wire is sound in the places it was tested: the password is write-only and
Redacted, decode errors don't echo it, cancellation reaches the handler, and a bad response fails
only its own request. Three things should be fixed in the contract before D, X and U* build on it:
`rows: unknown` kills the request on ordinary Postgres values (F2); the Desktop drops the
`E-DATA-*` code and fix (F3); and a 200-row unary `data.query` can't support the 10k grid (F4).
F1 (free-text fields that can carry a URL) and F5 (an approval RPC that bypasses the Agent
Session machine) are design calls for the Lead.

### F1 · P1 · Nothing on the wire keeps a URL or password out of free-text fields

The contract keeps only the password out of the Daemon's outputs. Five string fields take any text
and go to every Desktop window, and the agent tools will reuse them:

- `QueryLogEntry.author.command` (`:124`) is, by definition, the shell command of an "outside
  Polaris" Tool Call. The command the spec gives as its example, `psql postgres://app:pw@…`,
  carries the password.
- `DataSource.error` (`:48`), `QueryLogEntry.error` (`:130`) and `DataError.message`/`fix`
  (`:145`) carry driver or connection text, and the spec says `E-DATA-UNREACHABLE` returns "the
  reason".
- `DataSource.host` (`:35`) is `Name` (any string of one character or more), so a discovery bug
  that splits `user:pw@host` wrongly keeps the user and password in it.

Failing scenario (repro R2 below): a `QueryLogEntry` with
`command: "psql postgres://app:hunter2@db.internal:5432/app -c 'select 1'"`, a `DataSource` with
`host: "app:hunter2@db.internal"` and `error: "could not connect to postgres://app:hunter2@…"`,
and a `DataError` whose message is that URL all decode and encode; `hunter2` appears in the encoded
JSON every time.

Severity: P1, not P0, because nothing produces these values yet, and the command text is already in
the Agent Session's own Tool Call item. It becomes P0 the moment D or X fills these fields from a
raw command or driver text. Suggested fix: one `scrubCredentials` function in the protocol,
applied when these fields are built (a branded `ScrubbedText` schema whose decode strips
`scheme://user:pass@` userinfo and `password=` pairs), and `host` checked so it can't contain `@`,
`/` or `:`.

Held: `Bun.SQL`'s own connect errors carry no credentials. `new Bun.SQL("postgres://app:hunter2@127.0.0.1:1/app")`
and the same against MySQL and an unresolvable host all throw `"Failed to connect"`, with no
`hunter2` in any of the error's properties (Bun 1.4.4). D still has to wrap whatever text it
builds itself.

### F2 · P1 · `rows: unknown[][]` type-checks Date, bytes and bigint, then the request dies on the wire

`QueryResult.rows` is `Schema.Array(Schema.Array(Schema.Unknown))` over `RpcSerialization.json`.
`Bun.SQL` returns `Date` for `timestamptz`, `Uint8Array`/`Buffer` for `bytea`/`BLOB`, and `bigint`
for `int8` when asked. All of those type-check against the contract, and all of them kill the
request.

Failing scenario (repro R5, real Unix-socket transport):
`rows: [[12345678901234567890n]]` →
`Die("Expected JSON value at ["value"]["rows"][0][0]")`, and
`[[new Date(…), new Uint8Array([1,2,3])]]` → the same. The client gets a defect, not a
`DataError`, and the Daemon logs it as `RPC data.query died`. The spec's value rules (ISO 8601 with
the offset, `<bytes n>`, numerics as the database returned them) appear nowhere in the type.

Held: the connection survives, and the next `data.query` on it succeeds.

Suggested fix: a `DataValue` schema (`null | boolean | string | number | { _tag: "Bytes", length } | …`)
for `rows` and for `params`, so D's normaliser is forced by the compiler. `params` has the same
problem in the other direction: nested objects pass, and Date params from the renderer would die.

### F3 · P1 · The Desktop loses `DataError.code` and `fix`

`dataHandlers` maps every failure through `toIpcError`, which keeps only `_tag` and `message`.

Failing scenario (repro R4):
`toIpcError(new DataError({ code: "E-DATA-TIMEOUT", message: "statement timeout", fix: "narrow the query" }))`
returns `{"code":"DataError","message":"statement timeout"}`. The renderer can't tell
denied from read-only from timeout, and can't show the fix. U* would have to parse message text.
`Unsupported` also reaches the renderer with `message: ""`, because it has no message field.

Suggested fix: a Data-specific mapping in `ipc/data.ts`, with `code: error.code` and `fix` on
`IpcError`, plus a test.

### F4 · P1 · `data.query` can't carry the 10k grid

`limit` is 1–200 (`:178`) and there is no `offset`, cursor or stream. The DataQueries interface
says Desktop Queries share the agents' path (`apps/daemon/src/data/index.ts:59`), so the Table
tab and the SQL tab get at most 200 rows.

Failing scenario (repro R3): `limit: 10000` fails to decode, and the payload's only fields are
`sessionId, source, sql, params, limit`.

Cancellation: on the wire it works (repro R6: a client timeout interrupts the Daemon's handler).
But the Desktop request channel is `ipcMain.handle` with no abort, and `queryId` only comes back in
the result. So the renderer can't cancel a running Query, and the Query Log can't name one while it
runs. The subscribe channel already has unsubscribe.

Suggested fix: keep `data.query` (agent-sized, 200 rows) and add a Desktop `data.query.stream`
(`stream: true`). It sends a header chunk (`queryId`, `columns`), row chunks of about 500 rows, and
an end chunk (`rowCount`, `truncated`, `elapsedMs`), capped at 10,000 rows. The renderer opens it as
a subscription, so cancelling is unsubscribing, and every chunk stays under the frame cap (F6). It
belongs in C's contract now, before U* builds the grid on a 200-row unary call.

### F5 · P1 · `data.approval.decide` is a second approval path (PLAUSIBLE)

The spec says a Data Source Approval "goes through the Agent Session machine and the approvals in
`packages/spec`, never around them". The existing route is the `RespondToApproval` command
(`{sessionId, requestId, decision}`), granted to approve-grant Extensions and Linked Devices.
`data.approval.decide` is a separate RPC: keyed by `approvalId` with no `sessionId`, Desktop-only,
and carrying a `scope` that `RespondToApproval` can't express.

Failing scenario: X has two bad choices.
- (a) Resolve the approval from this RPC. The Engine then sees an approval settled outside the
  Agent Session machine, which is a bypass of the spec. The phone and the glasses show a needs-you
  approval that their only answer path, `RespondToApproval`, can't settle with a scope.
- (b) Route it through `RespondToApproval`. Then this RPC is dead weight, and `ApprovalDecision`
  needs a scope.

PLAUSIBLE because X hasn't built either yet. Decision for the Lead: extend `ApprovalDecision` with
an optional Data scope and drop `data.approval.decide`. Also decide whether an Extension or phone
with `approve` may grant a Data Source Approval at all; today the contract says Desktop-only for
Data while the approval route says otherwise.

### F6 · P2 · A response over 16 MiB dies

`MAX_FRAME_BYTES` is 16 MiB. Two hundred rows of a 100 KB `jsonb` or `text` column reach it, and
the spec's 200-character clipping applies to the agents' text, not to `structuredContent` or the
Desktop.

Failing scenario (repro R5): a single 17 MiB cell → `Die(FrameError: frame of 17825967 bytes
exceeds limit)`. The connection survives. Fix: chunked rows (F4) plus a per-cell byte cap with a
marker, enforced in the contract.

### F7 · P2 · `data` is advertised while every request is a stub

`daemonCapabilities` includes `"data"` (`serve.ts:214`), and the transport test asserts it. A
Desktop on a build cut from the integration branch between C and D/X shows "no Data Sources" (an
empty snapshot) and Unsupported on every action. Worse, one capability covers discovery, Queries,
the log and approvals, so a Daemon with D but not X can't say which half it has. Phase 2's
`execute` will need its own capability anyway.

Fix: advertise `data` only from the layer that implements it (D's discovery plus X's Query), or
split it (`data.sources`, `data.query`, `data.approval`).

### F8 · P2 · Gaps in the error codes

The six codes match the spec table exactly. That held. But:
- ADR 0091's MySQL allowlist refusal (a non-SELECT first keyword, `INTO OUTFILE`) isn't "the
  database refused a write" (`E-DATA-READ-ONLY`), and the spec gives it no code. X will improvise.
- A Query the user cancels has no code.
- `Errors` includes `NotFound` beside `E-DATA-UNKNOWN-SOURCE`, so an unknown source has two
  encodings.

Fix: a spec line saying the allowlist refusal is `E-DATA-READ-ONLY` with the fix "use `execute`",
an `E-DATA-CANCELLED` code (or say interruption is the signal), and `NotFound` either dropped from
`Errors` or reserved for `approvalId`.

### F9 · P2 · `QueryLogEntry` is missing state

- No `params`, so "any row re-runs into a SQL tab" (DESIGN) can't re-run a parametrised agent
  Query faithfully.
- No status (running, waiting for approval, dry run, cancelled), so the "needs-you row" DESIGN
  describes for a write waiting for approval can't be drawn.
- Is each emission the whole log or an append? The contract doesn't say. A whole-log snapshot per
  new Query sends O(n²) bytes over a long session, and there's no window or cursor.

Fix: add `params?` (scrubbed per F1), a `state` literal, and document snapshot-of-last-N plus a
`data.queryLog.page` request.

### F10 · P2 · Missing state changes for the user

`DataSource.writes` (`"ask" | "off"`) and `access` exist, but no RPC sets writes on a Remote Data
Source, and none revokes a remembered Data Source Approval ("Agent access…" in the connection
bar). `SaveDataSource.password` is optional with no way to say keep vs clear on Edit, and there is
no "previous name", so renaming is remove plus save (and the stored password is lost). Fix: a
`data.source.access` RPC (`writes`, `revoke`) and a password field of `keep | clear | set(Redacted)`.

### F11 · P2 · SchemaTree and QueryResult fields the UI needs

- The SQL tab's completion needs every table's columns. SchemaTree has column counts only, so U*
  needs one `data.describe` per table, up to 500 calls.
- "Schema loaded 4s ago" has no `loadedAt`.
- `rowCount` can't express the spec's own "200 of 18,402 rows" (returned rows vs total).

Fix: add `columns: [{name, type}]` to `TableSummary` (or a `columns: true` flag on describe), a
`loadedAt`, and split `rowCount` into `returned` and `total?`.

### F12 · P3 · Older Daemons: watches end empty, requests fail

`watchDataSources` and `watchDataQueryLog` return `Stream.empty` on an older Daemon, while requests
fail with Unsupported. This follows `hostStats.ts:34`. But a renderer waiting for the first
snapshot waits forever unless it also reads capabilities. Fix: document it in `data.ts`, or fail
with Unsupported like the requests.

### F13 · P3 · Imports above the module doc comment

In `serve.ts`, `feeds.ts`, `requests.ts`, `api.ts` and `contract.ts` the new import sits on line 1,
above the module doc comment, so the comment no longer heads the file. Lint passes; it's cosmetic.

## What was attacked and held

- **Password echo on decode failure.** An invalid port and an invalid label colour, with a
  password present, through both `SaveDataSource.payloadSchema` and the Desktop
  `DataRequestInputs["data.source.save"]`. The messages name the field and the expected value,
  never the input (R1). RpcServer sends `SchemaIssue.defaultFormatter(issue)` back on payload
  failure, so this is what a Client would see.
- **Password on the way out.** No success schema has a password field. The password is
  `RedactedFromValue`, so Effect logging of the decoded payload prints `<redacted>`. The Desktop
  main wraps it before forwarding, and the type requires a `Redacted`.
- **Driver error text.** `Bun.SQL` connect failures have no credentials (F1, Held).
- **Handler precedence.** `startServer` lets the caller's handlers win over `defaultHandlers`'
  Unsupported fallbacks, so the real Daemon serves `DataRpcsLive`.
- **Grants.** All eight RPCs are `client` and `local` in the exhaustive maps, and the protocol test
  covers Extensions and Linked Devices.
- **Old Client and new Daemon.** The new RPCs are additive to `DaemonRpcs`; an old Client never
  sends them. New Client and old Daemon: the helpers check the capability (F12 aside).
- **Cancellation on the wire.** A client timeout interrupts the Daemon's `data.query` handler (R6).
- **Defect isolation.** BigInt, Date, bytes and over-cap responses fail only their own request;
  the next call on the same connection succeeds (R5).
- **Error codes.** The six `DataErrorCode` literals and `{code, message, fix}` match the spec table.
- **Union decoding.** `SchemaTree | TableDetail` share no required field, so they don't decode as
  each other.

Not attacked: a real Postgres or MySQL (there's no execution yet), the renderer (U* hasn't been
built), and Apalache.
