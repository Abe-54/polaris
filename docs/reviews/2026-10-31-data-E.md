# Adversarial review: E, grid edits, Commit ⌘S and the remote bulk confirm (ENG-645)

Reviewed: `41d0f2e6` (merged in `1382c3bc` on `polaris/grill-with-docs-i-want-to-do-7ce3`), diffed
against `075aac5e`: the editors (`apps/desktop/src/renderer/features/data/grid/`), the staged model,
store and commit (`ui/table/edits/`), and the path E commits through, W's `data.edits.commit`
(`apps/daemon/src/data/writeEdits.ts`, `writeExecution.ts` `executeEdits`, `execution.ts`
`bindValues`). Read against DESIGN.md → Data (Table tab), the E claim's decisions and RW's review
(`2026-10-30-data-W.md`). Reviewer: RE, Opus 5.5, 2026-10-31. No product code changed.

**Verdict.** The staging model is sound: counts are exact, undo works, edits survive tab switches,
the remote confirm counts rows and cells correctly and single-row commits skip it, and 2,000 staged
edits on a 10,000-row table cost nothing measurable. Five things should be fixed before Data ships:
- On Postgres, every JSON or JSONB edit is stored as a JSON **string**, not the object the user
  typed. The commit reports success (F1).
- A commit overwrites whatever an agent wrote to the same cells since the user staged them, without
  a word (F2).
- A table whose primary key isn't declared in column order can never be committed; "Reload the
  table" doesn't help (F3).
- ↵ ↵ or clicking away from an untouched editor stages a change on integer, timestamp, MySQL
  boolean and CRLF text cells. Committing it writes the stale value back (F4).
- A staged row that an agent deletes becomes an invisible edit that fails every later commit (F5).

### F1 · P0 · Postgres JSON edits are stored as strings

`bindValues` (`execution.ts:106`) binds a `Json` value as its text. Bun.SQL serialises a JS string
for a `json`/`jsonb` parameter as a JSON string, so the column receives a string scalar that
contains the user's JSON.

Probe P3 through `executeEdits`, then a minimal repro on Bun.SQL alone:

```
postgres P3 j big number: {"ok":1}
stored j::text = "\"{\\\"a\\\": 12345678901234567890, \\\"b\\\": 1, \\\"b\\\": 2}\""
UPDATE "public"."re_json" SET "j"=$1, "k"=$2 WHERE "id"=$3  ['{"a":2}', '{"a":2}', 1]
→ j: "\"{\\\"a\\\":2}\"", jsonb_typeof: string; k: same, json_typeof: string
```

The user edits a JSON cell, commits, and sees "Committed 1 change · 1 row". The written overlay
shows the intended object until the rows are read again. Every `j->>'a'` in the app now returns
NULL. MySQL stores the object correctly.

The same binding is used for an agent's `execute` parameters (W's path), so `Json` params there
are affected too.

Fix: on Postgres, cast the text in SQL (`$1::text::jsonb`, or `CAST($n AS <column type>)` from the
catalog) rather than binding a JS string to a json-typed parameter. Don't `JSON.parse` it: that
rounds 20-digit numbers. Add a real-database test that reads `jsonb_typeof` after a grid commit.

### F2 · P1 · A commit overwrites what an agent wrote since the user staged

`editStatements` writes `UPDATE t SET col = $new WHERE pk = $key`. The staged cell's `before` is in
the store but never sent or checked. Probe P5:

```
user saw [[1,10,100],[2,20,200]]; an agent then sets v = 99 on row 1
commit v = 11 → {"ok":1}; after [[1,11,100],...]   (both engines)
```

The agent's 99 is gone, and nothing on either side says so. This is the expected case in Polaris:
agents write to the same tables the user is looking at. With F4, a cell the user never meant to
change can carry the stale value. The commit is atomic (all-or-nothing works, see F5); it just isn't
checked against what the user saw.

Fix: send each cell's `before` and add `AND col IS NOT DISTINCT FROM $before` (MySQL `<=>`) per
changed column. On 0 rows, fail with `E-DATA-CONFLICT` naming the row and column, and have the grid
mark that cell ("Changed since you staged it · was 10, now 99") with Keep mine / Take theirs.

### F3 · P1 · Composite keys out of column order can't be committed

The Desktop builds the key from the table detail in column order (`useTableEdits.ts:50-51`). The
Daemon reads it in constraint order (`writeTable.ts`, `ORDER BY k.ord` / `ORDINAL_POSITION`) and
compares the two with `JSON.stringify` (`writeExecution.ts:340`). Probe P1, table
`(a INT, b INT, v INT, PRIMARY KEY (b, a))`:

```
postgres/mysql: sent ["a","b"] → E-DATA-SQL "The table's primary key does not match these edits." fix "Reload the table before editing it."
               sent ["b","a"] → {"ok":1}
```

Reloading changes nothing, so every edit to such a table fails forever, even though the cells look
editable. Junction tables are often declared this way.

Fix: compare the keys as sets on the Daemon and reorder `edit.key` to the constraint order, or have
the catalog return the key order and use it on the Desktop.

### F4 · P1 · Untouched editors stage phantom changes

`parseDraft` returns a differently shaped value from the one the cell held, and `stage` compares
them with `JSON.stringify`:
- int4 `42` (a number) → `Numeric {value: "42"}`.
- timestamptz `Timestamp {iso: "…T06:30:00.123456+00:00"}` → `Timestamp {iso: "… 06:30:00.123456+00:00"}`.
- Postgres `timestamp` arrives as a string and comes back as a `Timestamp`.
- MySQL `tinyint(1)` `1` → `true`.
- Text with `\r\n` opens a textarea, which normalises it to `\n` (Chrome 152: `"line one\r\nline two"` →
  `"line one\nline two"`).

Probe R1 (↵ then ↵, no typing), with real value shapes:

```
R1 {"int4":"1 change staged · 1 row","timestamptz":"1 change staged · 1 row","tinyint(1)":"1 change staged · 1 row", "jsonb":"nothing staged"}
R2 (open, then click away) "1 change staged · 1 row"
```

The CRLF case only shows in Chromium; happy-dom doesn't normalise. ↵ inspects in other grids, and
the editor stages on blur, so just looking at a cell is enough to stage one. The cell turns tan and
the footer counts it. On a remote source, two such looks open the bulk confirm. Committing writes
the old value back, which overwrites an agent's newer value (F2) and fires `updated_at` triggers. A
CRLF cell is rewritten to LF.

Fix: compare in the column's terms before staging (`sameValue` after normalising: numbers by
decimal value, timestamps by instant plus offset, `0/1` against booleans). Don't stage on blur when
the draft is untouched. Keep `\r\n` by remembering the original line ending, or by editing CRLF text
in a field that doesn't normalise.

### F5 · P1 · A deleted row's staged edits become invisible and block every commit

`overlay` skips staged cells whose key isn't in the rows (`staged.ts:140-147`), but `countStaged`
and `editsInput` still include them. Probe R5 (stage a cell on row 2, re-read without row 2):

```
R5 footer: "1 change staged · 1 row" | staged cells shown: 0
```

Committing then fails (probe P5, both engines): `E-DATA-SQL` "An edit affected 0 rows instead of
one. All edits were rolled back." fix "Reload the table and stage the edits again. Your edits are
still staged." Reloading doesn't bring the row back, the message doesn't say which row, and the only
ways out are Discard (everything) or ⌘Z back past every later edit. The same happens when an agent
changes the key, and when a filter hides the row: hidden edits still commit, with no confirm on a
Local source.

Fix: say "N changes on rows not shown" in the footer, with a way to list them or drop them. Have the
Daemon fail with the missing key so the Desktop can mark those cells "Row no longer exists" and offer
Drop.

### F6 · P2 · Offsets on columns without a zone

`parseTime` accepts any offset and only requires one on a zoned column. The hint for every time
column is "2026-08-02 09:30:00+00:00". Probe P3, staging `2026-08-02 09:30:00+05:30`:

```
postgres timestamp   → 2026-08-02 09:30:00   (offset dropped)
postgres timestamptz → 2026-08-02 04:00:00+00
mysql DATETIME       → 2026-08-02 04:00:00   (converted to the session zone +00:00)
```

The two engines disagree, and both differ from what the grid shows from the written overlay
("09:30:00+05:30").

Fix: refuse an offset on a column without a zone ("This column has no time zone; write a local time"),
and show the hint without one.

### F7 · P2 · Numbers that don't fit the column

`NUMBER` accepts fractions and exponents for every numeric column. Probe P3 on `INT`:

```
postgres '1e3' / '.5' / '2.7' → E-DATA-SQL invalid input syntax for type integer, fix "Check the statement and parameter types."
mysql    '1e3' / '.5' / '2.7' → ok; stored 2.7 as 3
numeric(10,2) '1.005'        → stored 1.01 (both)
```

After a successful commit the grid keeps showing `2.7` and `1.005` from `written`
(`commit.ts:103`) until the rows are read again. E already listed the missing re-read as a
follow-up; this is the case where the overlay is wrong, not just stale.

Fix: check integers against `int*`/`serial`/`bigint` in the editor, check scale against
`numeric(p,s)`, and re-read the committed rows (or have the Daemon return them) before clearing the
tint.

### F8 · P2 · Commit errors speak to agents

The footer shows `{code} · Commit failed · {message}` and `{fix} Your edits are still staged.` The
fixes come from the Daemon's agent-facing errors:
- `E-DATA-SQL`, "Check the statement and parameter types." The user wrote no statement.
- `E-DATA-DENIED`, "The user can allow writes for this target in Data." Seen when another Client
  turns writes off between staging and commit.
- "Reload the table and stage the edits again. Your edits are still staged." This contradicts
  itself, and reloading doesn't help (F5).
- `E-DATA-TIMEOUT`, "Narrow the query and try again."

None of them names the row or column that failed. E's screenshot `edit-error-dark.png` shows a
fixture fix ("Shorten the value, or change the column through a migration.") that the Daemon never
sends.

Fix: map the commit's errors to user copy on the Desktop (by code, plus the failing key and column,
which the Daemon should return). Keep the agent fixes for MCP.

### F9 · P2 · ⌘S inside the editor does nothing

`CellEditor`'s keydown calls `stopPropagation()` (`:166`), so the window listener that runs
`data.commitEdits` never sees ⌘S. Menu accelerators aren't registered (`registerAccelerator =
false`), so nothing else catches it. Probe R3b, with `installKeyboard` on the real registry:

```
R3b sent from the field: 0 | sent from the grid: 1
```

Typing a value and pressing ⌘S is what every editor teaches. Here the value stays in the open editor
and nothing commits.

Fix: in the editor, ⌘S stages the draft (if valid) and then runs `data.commitEdits`.

### F10 · P2 · IME composition

`onKeyDown` stages on any Enter (`:171`) without checking `event.nativeEvent.isComposing` (or
`keyCode === 229`). Probe R4: draft `にほn`, Enter with `isComposing: true` closes the editor with
`にほn` staged. The candidate the user was confirming is lost.

Starting an edit by typing (`typedKey`, `DataGrid.tsx:71-74`) needs `event.key.length === 1`. A
composition starts with `Process`, and macOS ⌥ characters (é, ø) are excluded by `!altKey`, so
neither starts an edit. The app's own `keyboard.ts:81` already skips composing events.

Fix: ignore Enter while composing. Open the editor on `compositionstart` and let ⌥-typed characters
through.

### F11 · P2 · Multi-line paste into a single-line cell

A text cell without a line break edits in an `<input>` (`:116`). Chrome 152 turns pasted `x\ny` into
`x y`, and the value setter strips newlines entirely. A pasted address or note loses its line breaks
with no notice.

Fix: use the textarea for every text column (Shift+↵ for a new line, as JSON does), or switch to it
on a paste that contains a line break. Say the new-line chord in the text hint.

### F12 · P2 · Losing staged work

The edits store is in memory only. A window reload or ⌘Q with staged edits loses them without asking
(no `beforeunload` or quit hook anywhere in the Desktop App). Closing a tab asks, so the two
behave differently.

Discard (`TableData.tsx:135`) drops every staged edit in one click with no confirm, and ⌘Z can't
bring them back. Probe R6: 2 edits, Discard, ⌘Z → nothing staged. DESIGN.md's Changes tab says
"Discard always asks … Cancel focused". The Table tab's Discard should follow the same rule, or keep
the discarded set for one ⌘Z.

### F13 · P2 · "Read only" Local sources are editable

`writesBlocked` returns null for every Local source (`commit.ts:29`), whatever `writes` says. A
source the user set to "Read only" opens editors and commits, because the Daemon doesn't check it
either (RW F2). Once WF refuses it on the Daemon, the grid will still offer editing and only fail at
commit. Fix both: treat `writes: "off"` as read-only on either locality, with the same footer reason
and "Connection…".

### F14 · P3 · Float keys

Probe P4: a Postgres `REAL` key stored as 0.1 reads back as `0.1` and `WHERE r = 0.1` matches 0 rows,
so the commit fails (F5's message). MySQL `FLOAT` matched. Rare as a key, but the table looks
editable. Mark `real`/`float4` keys as unmatchable ("This row's key is a floating-point value") like
binary keys.

### F15 · P3 · Closing a tab during a commit

While a commit is running, the close dialog still says "Discard staged changes … Discard and close".
The request is already on its way and lands anyway. When it answers, `runCommit`'s `changeEdits`
recreates the tab's entry in `editsStore` after `dropTab` removed it, so reopening the table shows
"Committed …" or the old error. Fix: don't offer Discard while committing ("Committing… close when
it lands"), and ignore results for dropped tabs.

## Checked and fine

- Counts: "N changes staged · M rows" and the confirm's "Commit 3 changes to 2 rows?" count cells
  and distinct keys exactly. Single-row commits skip the confirm; a Local source never confirms.
- Remote writes: `access` not approved or `writes: "off"` is read-only with the reason and
  "Connection…". The Daemon requires `ask` + approved for a remote commit. The confirm's bar takes
  the label's colour, Cancel is focused, and ↵ cancels.
- Atomicity: a statement that fails or matches 0 rows aborts the whole commit (P5's two-row commit
  failed as one; W's `writeExecution.real.test.ts` checks the rollback). MySQL reports matched rows,
  so a no-op `UPDATE` counts 1 and doesn't trip the count check (P2).
- Keys: microsecond `timestamptz` and `DATETIME(6)` keys, and 30-digit `numeric` keys, round-trip
  and match. Very long keys arrive `Truncated` and are refused.
- NULL, `''` and `'NULL'` stay distinct: NULL is a toggle, typed `NULL` is text. 1 MB text commits
  on both engines.
- Undo is unlimited and per cell; edits survive tab switches and remounts; each Agent Session has
  its own.
- Both themes and three densities in E's committed screenshots: the tan ground and ring read in
  light Compact, the confirm in production red and the error panel are legible. E adds no motion
  of its own (only `@polaris/ui`'s Dialog). The staged tint is `git-modified`, which `-cvd` doesn't
  remap, and no diff colours share the Table tab.
