What I checked and found sound:
- **NODE_OPTIONS quoting**: `appendNodeImport` writes `--import "<file URL>"`. File URLs percent-encode spaces and quotes, so Node's `NODE_OPTIONS` parser sees one token. The user's own options are kept byte-for-byte.
- **Bun children**: Bun ignores `NODE_OPTIONS --import`, so a missing file there doesn't break Bun (`bun -e` exits 0). `register.mjs` also guards on `process.versions.bun`.
- **P2 tokens**: the Turn ids come from the HMAC-signed payload, the binding is checked against the session's full Turn history (`sessions.ts:142-150` reads every Turn), and the env file is 0600 inside a 0700 `mkdtemp` directory.
- **Forwarding fetches**: they use `redirect: "manual"`.

## P3: auto-instrumentation

### P3-1 (P1): an app SDK that detection misses loses its own spans

`prepareAutoInstrumentation` (`instrumentation/index.ts:41-55`) skips only when a manifest **on the path from the launch cwd up to the checkout root** lists `@opentelemetry/sdk-node`, `@vercel/otel` or `@opentelemetry/sdk-trace-*` (`package.ts:38-42`).

The launch cwd is the terminal's or the Agent Session's cwd (`instrumentation/runtime.ts:58`, `session?.cwd ?? cwd`), not the directory where `node` later starts. Anything detection can't see still gets the preload:
1. A monorepo package's SDK, when the terminal or session opened at the checkout root and the command `cd`s into the package.
2. An SDK reached through a vendor wrapper, such as `@honeycombio/opentelemetry-node`, `@sentry/node` v8+, `@azure/monitor-opentelemetry` or `dd-trace`.
3. An SDK preloaded through the user's own `NODE_OPTIONS`: `--import @opentelemetry/auto-instrumentations-node/register` is OTel's documented zero-code setup. Polaris prepends its import (`index.ts:66-69`), so it runs first.

Our preload's `NodeSDK.start()` registers the global tracer provider first. The app's own `sdk.start()` then can't register, and nothing is logged, because the diag logger is a no-op by default. `trace.getTracer()` in app code returns Polaris's provider, so manual spans go only to Polaris. The app's exporter receives nothing, and both SDKs' HTTP instrumentation patches the same modules.

`p3/preload.test.ts` "finding P3-1" covers the three cases. Each runs a real app that starts `NodeSDK` with an exporter to its "vendor" and ends one manual span. Each case reads `vendor: []`, and the span arrives at the "Polaris" counter instead. With auto-instrumentation off, each reads `vendor: ["app-manual-span"]`.

This undoes P1's aim that the app's own exporter keeps working: unless the user has also set up forwarding, the vendor silently loses the app's custom spans.

Fix direction: decide in the child, not at launch. `register.mjs` can run the check from `process.cwd()` and the entry's package, resolving known SDK and wrapper packages. It can also skip when `NODE_OPTIONS` already imports or requires another OTel register. Better still, never claim the global provider: register only Polaris's instrumentations with Polaris's own provider. Then an app SDK that starts later still owns `trace.getTracer()`.

### P3-2 (P1): a preload that disappears breaks every `node`

`bundledRegisterPath` (`assets.ts:37-58`) caches the materialized path per home for the life of the Daemon and never checks that it still exists. If `~/.polaris/node-instrumentation/` is removed while the Daemon runs (cleanup, a reset, a disk-cleaning tool, or a test fixture), every later terminal and Agent Session gets `NODE_OPTIONS=--import "file:///…/register.mjs"` pointing at a missing file. Node treats a missing `--import` as fatal:

```
Error [ERR_MODULE_NOT_FOUND]: Cannot find module '/tmp/rp1/missing.mjs'
Node.js v24.22.1        (exit 1)
```

Every `node`, `npm`, `npx`, `tsc` and test runner in those shells fails until the Daemon restarts. Terminals opened earlier also break as soon as the directory goes, since their environment can't be updated.

The same failure happens wherever the inherited `NODE_OPTIONS` crosses into a place where the path doesn't exist. The usual case is Docker Compose passthrough (`environment: [NODE_OPTIONS]`), which runs `node` inside a container that can't see the Host's `~/.polaris`.

`p3/preload.test.ts` "finding P3-2": prepare, delete the directory, prepare again, run `node -e`. It reads `{ code: 1, missing: true }`.

Fix direction:
- Re-check that the file exists before reusing the cached path, which is cheap.
- Make a missing file harmless. One way is to inject `--import "data:text/javascript,import('file:///…/register.mjs').catch(()=>{})"`: Node accepts `data:` URLs for `--import`, and a failed dynamic import doesn't stop the app.

### P3-3 (P2): an inherited preload from another build doubles every span

`appendNodeImport` (`nodeOptions.ts:16-33`) treats an existing import as the same only when its URL is identical. Assets are content-addressed (`assets.ts:15-16`), so a different Daemon build has a different digest directory. If the source environment already carries a Polaris preload under another digest, both stay: for example, a Daemon started by hand from a Polaris terminal, or a terminal opened before an upgrade. Each preload starts an SDK, so every span is exported twice. Node also prints `Warning: The 'import-in-the-middle' hook has already been initialized` on every start, which breaks tools that read stderr.

`p3/preload.test.ts` "finding P3-3" reads `{ spans: 2, warning: true }` for one `fetch`.

Fix direction: recognise any `…/node-instrumentation/*/register.mjs`, or a marker query on the URL, and replace it. Also add a process-global guard in `register.mjs` and `sdk.ts`, keyed on a `Symbol.for(...)` flag.

### P3-4 (P2): ~70 ms on every Node start

`sdk.cjs` is 1.36 MB minified and includes the gRPC, Prometheus and Zipkin exporters that `NodeSDK` pulls in. The module's `import` declarations run before the `if (endpoint …)` check in `sdk.ts:1-15`, so the whole bundle loads even when `POLARIS_OTEL_ENDPOINT` is unset. I timed `node -e 0` on this Mac, five runs each:

| | ms |
|---|---|
| plain | 38–40 |
| preload + endpoint | 106–111 |
| preload, no endpoint | 103–107 |

Every Node process in an instrumented shell pays this cost, including `npm` itself, every `npx`, `tsc`, eslint, and each test-runner worker. `npm` is a Node script, so its own registry traffic also becomes spans under the app's service name.

Fix direction:
- `require` the SDK inside the endpoint check.
- Build on `sdk-trace-node` plus the two HTTP exporters instead of `NodeSDK`, to drop gRPC, Prometheus and Zipkin.
- Run the `idle`/`terminal` benches with a Node-heavy scenario, not only the Daemon's own process tree.

### P3-5 (P2): the Harness process itself is instrumented

`TraceRuntime.environment` returns the preload, and `ClaudeDriver.ts:349-380` puts that environment on the Claude Code process (`env: childEnv({ …, ...traceEnv })`). Codex puts it in `shell_environment_policy.set` (`CodexSession.ts:189-203`), which is the right place for Codex.

`claudeExecutable` supports a Node-script Claude Code (`executable.ts:58-66`, `executable: "node"`). In that case Claude Code itself runs with the SDK loaded, under `import-in-the-middle`. Its HTTPS calls to the model API become spans named after the app's package, are stored in the checkout's Traces, and are forwarded to the vendor. The native Claude binary ignores `NODE_OPTIONS`, but its stdio MCP servers inherit the variable: `npx` servers are Node, and so is npm.

P2's per-command hook already carries the environment for each Bash command, so the Harness process doesn't need `NODE_OPTIONS`. Not run here: this Host's `claude` is a native binary.

Fix direction: keep `NODE_OPTIONS` and `POLARIS_OTEL_*` out of the Harness process's environment and out of the MCP servers' environments. Inject them only per command (Claude) or through the shell policy (Codex).

### P3-6 (P3): partial writes and growth

`materializeInstrumentation` writes with `flag: "wx"` and treats a mismatched existing file as an error (`assets.ts:24-31`). If the Daemon dies mid-write, the truncated file makes every later prepare fail with "The bundled Node instrumentation could not be prepared." That lasts until someone deletes the directory by hand. It fails safe (nothing is injected) but never recovers on its own.

Each build whose assets change also leaves a ~1.5 MB directory under `node-instrumentation/` that is never pruned. Keeping old builds is deliberate, for terminals opened before an upgrade, but nothing bounds the number kept.

Fix direction:
- Write to a temporary file and rename it into place.
- Prune directories that no live terminal or session needs, for example after N newer builds.

## P1: forwarding

### P1-1 (P1): metrics stop reaching the app's collector

Before P1, the runtime didn't inject when the launch environment already exported (`git show 9a0fac480^1:apps/daemon/src/traces/runtime.ts`, lines 22-23 and 109). P1 always injects `OTEL_EXPORTER_OTLP_ENDPOINT` plus the traces and logs endpoints (`runtime.ts:218-222`) and forwards traces and logs. The receiver only accepts `/v1/(traces|logs)` (`receiver.ts:145`).

OTel SDKs derive the metrics URL from the base endpoint, so an app that exported metrics to its collector now posts them to the receiver, gets 404, and its metrics dataset silently goes empty. Claude Code's own OTel metrics have the same problem when the user enabled them.

`p1/metrics.test.ts` "finding P1-1" reads `{ status: 404, vendor: [] }`.

Fix direction: when a collector is known, set `OTEL_EXPORTER_OTLP_METRICS_ENDPOINT` to the user's metrics URL, resolved from their own environment. Otherwise, accept `/v1/metrics` and forward it without storing.

### P1-2 (P2): the app's own headers are forwarded, and override configured ones

`forwardHeaders` (`forwardQueue.ts:171-176`) starts from the configured headers, then copies **every incoming request header** from the app over them. Only hop-by-hop headers and `proxy-*` are removed.

The existing test `forwarding.test.ts` "receiver forwards exact … bytes and headers" asserts that `authorization: Bearer private-constructor` reaches the target. Settings shows `forwardTo.headerNames` only from the configured headers (`detection.ts`, `publicCollector`). A saved target from Set up tracing has no configured headers (`settings.ts`, `policy` fallback), so the card says no headers will be sent. In fact every forwarded request carries whatever the app's exporter sends, which is usually the user's `OTEL_EXPORTER_OTLP_HEADERS` credential from their shell.

Here is how that sends a credential to a destination the repository controls, even after SEC1's fix. A user accepts a suggested target taken from a committed `.env`, while their shell holds the vendor key in `OTEL_EXPORTER_OTLP_HEADERS`. The repository's endpoint then receives the key. That shell-key / `.env`-endpoint split is common.

Fix direction:
- Forward only the configured headers and `content-type`. Drop `authorization` and other credential-like headers that the app sent but nobody configured.
- Or list the forwarded incoming header names in Settings, and require the target to be one the user typed.
- Either way, SEC1 should decide alongside ENG-696.

## P2: launch attribution

### P2-1 (P1 if confirmed): the command rewrite is user-visible

The PreToolUse hook (`harness/claude/traces.ts:62-94`) returns `updatedInput.command = ". '<tmp>/polaris-launch-…/<uuid>.sh'\n" + command` for every top-level Bash call while tracing is available. That holds in every permission mode except read-only. P3's `launchInstrumentation` treats plan mode as read-only, but this hook doesn't.

Every P2 test runs in `full-access` (`launch.test.ts:59, 221, 265`). If Claude Code evaluates permissions on the hook's updated input, as the SDK's PreToolUse `updatedInput` contract suggests, then in default, acceptEdits and plan modes:
- `canUseTool` gets the rewritten command, so Polaris's approval card (`ClaudeDriver.ts:320`, `describeToolCall`) shows the temp-file line.
- Claude's "always allow" suggestions are computed for a command holding a unique temp path, so they never match again.
- Allow rules like `Bash(npm test:*)` and plan mode's read-only Bash auto-allow may stop matching: `. file` isn't read-only.

Not verified: it needs one live default-mode Claude run, which I didn't make.

Fix direction:
- Confirm with one default-mode run.
- If confirmed, look at `CLAUDE_CODE_SHELL_PREFIX`. A fixed wrapper could fetch the current endpoint from the Daemon per command, without changing what permission checks see.
- At minimum, skip plan mode, as P3 does.

## Build and dependencies

### Build equivalence (Lead's point 2)

The `Bun.build` call matches the earlier `bun build` CLI:
- **Entrypoints**: the same four (`main.ts`, `fffWorker.ts`, `traces/worker.ts`, `traces/profiles/worker.ts`).
- **Splitting and minify**: `splitting: true`; `minify: true` equals `--minify`.
- **Defines**: each `KEY=VALUE` is split at its first `=`, and no value contains another, so `FFF_LIBC="gnu"` and the others compile identically.
- **Compile target**: `compile: { target, outfile }`.
- **Signing**: `signAdHoc` still runs on the output afterwards.
- **Errors**: `result.success` is checked.
- **Autoload defaults** are the same for the CLI and the API. I built the same probe both ways: each loaded `.env` from its cwd and ran `bunfig.toml`'s `preload`.

P3's binary smoke covers the traces worker and the extracted preload, and `selftest` covers the fff worker. No smoke exercises the Profiles worker in a compiled binary. Linux and Windows targets weren't built.

### B-1 (P2, existing behaviour): the compiled Daemon reads `.env` and `bunfig.toml` from its cwd

I compiled a probe through `Bun.build({ compile })` and ran it in a directory holding `.env` (`FOO=from-dotenv`) and `bunfig.toml` (`preload = ["./pre.ts"]`). It printed `bunfig preload ran` and `FOO=from-dotenv`. The CLI build behaves the same, so P3 didn't introduce this.

The service managers start the Daemon in `/`, `$HOME`, or the Windows task's `polarisHome`. A `polaris serve` started by hand inside a checkout, though, loads that checkout's `.env` into `process.env`. SEC1's precedence and P1 treat `process.env` as the trusted launch environment. It also runs the checkout's `bunfig.toml` preload inside the Daemon.

Fix: pass `compile: { target, outfile, autoloadDotenv: false, autoloadBunfig: false }`.

### B-2 (P3): the embedding plugin can silently not fire

`instrumentationPlugin` matches `/traces\/instrumentation\/embedded\.ts$/` (`build.ts:62`). A build run on Windows, with backslash paths, or any later move of the file, ships `embeddedInstrumentation = null`. The binary then falls back to `import("./build.ts")`, which needs `node_modules`, and every launch would report "could not be prepared". Nothing fails the build.

Fix direction: accept both separators, and fail the build if `onLoad` never ran.

### D-1 (P3): OTel versions (Lead's point 3)

Runtime child bundle (`sdk.cjs`):
- `api@1.10`, `resources@3.0`, `sdk-logs@3.0`, `sdk-node@0.300` and `core@3.0` are mutually consistent: their peers are `api >=1.10 <1.11`.
- The bundled API registers the global under `opentelemetry.js.api.1`. An app's own `@opentelemetry/api` up to 1.10 is compatible with it. An app on 1.11 or later would see a no-op API (OTel's minor-version check). Note this for later upgrades.

Daemon devDependencies:
- `sdk-trace-base@2.7` declares peer `api >=1.3.0 <1.10.0`, and `@vercel/otel@2.1.1` declares peers `resources <3`, `sdk-logs <0.300` and `instrumentation <0.300`.
- Bun's isolated linker links `sdk-trace-base@2.7`'s `api` to the single installed 1.10. Only `@opentelemetry+api@1.10.0` is in `node_modules/.bun`, so it is outside the declared range but works.
- `@vercel/otel` gets nested `resources@2.7` and `sdk-logs@0.213`.
- `bun.lock` also records nested `api@1.9.0` entries that the isolated install never materializes. A hoisted install would materialize them, putting two API copies in the sender fixtures.
- `senders.test.ts` and `forwarding.test.ts` pass (10 pass, 0 fail) on the current install.

Daemon runtime: the receiver's `otlp-transformer@0.213` still pulls `sdk-trace-base`, `resources` and `core` at 2.6 (decode only, no global API use).

Recommendation: move the fixtures to `sdk-trace-base` 3.x when `@vercel/otel` supports it, or document the isolated-linker assumption next to the devDependencies.
