# UF13: Harness isolation and Bash permissions (ENG-657, ENG-673)

## P2-1: confirmed

On 2026-10-31 (Host local date), the installed Claude Code 2.1.316 ran with
`permissionMode: "default"`, `settingSources: []`, and a PreToolUse callback returning
P2's exact rewrite shape. A signed-in Haiku request asked it to run
`node -e 'console.log(123)'` once. The permission callback denied execution after
recording the input and `describeToolCall` result.

Observed `canUseTool` input:

```json
{"command":". '/tmp/uf13-permission-probe/env.sh'\nnode -e 'console.log(123)'","description":"Run node one-liner that prints 123"}
```

`describeToolCall("Bash", input).detail` was the same rewritten command. Permission
suggestions were `[]`. Claude's result included that rewritten input in
`permission_denials`. Thus this is a permission-boundary failure, not just a
rendering problem. This run exercised the real signed-in Claude binary and model;
the callback denied the tool, so it did not execute the command.

A separate deterministic run drove the same installed binary with the repository's
fake Anthropic Messages API. It reproduced both the rewrite and the empty
suggestions. With an unchanged command and a pass-through shell prefix instead,
`canUseTool` and the formatter received the original command, and Claude suggested:

```json
{"type":"addRules","rules":[{"toolName":"Bash","ruleContent":"node -e 'console.log(123)'"}],"behavior":"allow","destination":"localSettings"}
```

The approved command printed `123`. The fake API determines the tool request;
Claude's actual permission engine, SDK transport and shell launch run unchanged.
It does not establish behavior on older Claude versions.

The shell-prefix probe also confirmed that `$1` contains Claude's assembled shell
setup and `eval '<original>'`, not a tool-use identifier. The documented prefix
also wraps hooks and stdio MCP startup. An unconditional environment export there
would instrument MCP servers. Matching command text would make identical concurrent
commands ambiguous. The Lead selected post-approval injection rather than a shell-prefix wrapper.

Native probes: `/tmp/uf13-probe.ts`, `/tmp/uf13-prefix-probe.ts`,
`/tmp/uf13-live-probe.ts`; signed-in output: `/tmp/uf13-live-probe.log`.
These temporary artifacts are local evidence; they are not shipped product files.

## Implemented boundary

All Harness process launch sites use `harnessEnv`, including the shared Codex
app-server, ACP children, OpenCode, and metadata probes. It removes every
`POLARIS_OTEL_*` key and uses UF11's `stripNodeInstrumentation` to remove Polaris
preloads while preserving unrelated Node options. Claude's session endpoint stays
available for explicit SDK exporters; its auto-instrumentation preload never
reaches the Harness or inherited stdio MCP environment.

In full-access, the Bash hook keeps its per-command rewrite. In supervised/default,
auto-edits/acceptEdits and auto, the hook records the launch Turn and original
command under `tool_use_id`, returning no modified input. The original command
passes through Claude's permission rules, Polaris's approval card and the rule
suggestions. Only an allowed `canUseTool` result gets the launch environment via
`updatedInput`; the permission result's remembered rules remain unchanged.
Plan mode never injects, including a mode change while approval is outstanding.
Denied, cancelled, unbound Subagent and unknown tool-use calls do not inject.
Completion hooks remove metadata for auto-approved calls; scope disposal clears
all remaining entries and private launch files. The map is bounded at 1,024
entries; overflow loses instrumentation rather than attributing another call.

Auto-approved commands intentionally run unchanged. They have no automatic
preload and no per-command launch attribution. The Lead authorized this boundary;
[ENG-697](https://linear.app/luxdev/issue/ENG-697/trace-commands-auto-approved-by-allow-rules-no-canusetool-callback),
related to ENG-673 and targeted at Polaris 0.8.0, tracks execution-only tracing
for commands that skip `canUseTool`.

## Regression evidence

The always-run permission regression tests pass for supervised, auto-edits and
auto. They execute a real Bash child and authenticate its endpoint as Turn 2 after
the hook's current Turn has changed to Turn 5. Additional cases cover denial,
cancellation, a plan-mode transition during approval, and auto-approved execution
with completion cleanup. Removing post-approval injection makes all three
permission-mode attribution cases fail at the observed launch Turn assertion.

## Accepted integration: a3320418c

Merged `a3320418c98b9ef988c2950af71a87ac899a0bb5`, including the accepted UF11
helper, SEC1, SEC2, P9 and RP4. Dependencies were synchronized with
`bun install --frozen-lockfile` without lockfile changes.

The native regression test passes on Claude Code 2.1.316 with the scripted Messages
API, real permission engine, a Node stdio MCP server, Bash, Node and the real OTLP
receiver. The observed input, approval detail and remembered rule are all
`node app.mjs`. Exactly one approval occurs for two calls. The first prints
`instrumented:true` and produces two spans attributed to its launch Turn; the second
matches the remembered allow rule and prints `instrumented:false`. Both execute
successfully. The MCP server's captured environment contains neither a Polaris
preload nor any `POLARIS_OTEL_*` variable.

The initial test fixture disabled all settings sources, so its remembered local
rule could not apply and it asked twice. Enabling only `local` settings in the
disposable checkout corrected the fixture; no user or project settings are loaded.
The other 14 focused cases passed, including all existing P2 launch tests. Removing
environment stripping causes both the canonical-name and mixed-case inheritance
regressions to fail. Targeted format/lint checks pass with the final implementation.

## Performance evidence

Three quick sessions runs on the accepted integration and three on UF13 completed
under the same lease. Integration measurements temporarily restored every tracked
modification to HEAD, then restored the UF13 bytes in a `finally` block. The added
tests/reports remained untracked, so both artifacts label the tree dirty.
The integration already exceeds the historical Mac14,13
baseline for initial RSS (103.0 to 122.4 MiB). UF13 versus that integration reports
one regression: m10c3 dispatch-to-event p99, 7.63 to 18.75 ms. Background load differs
substantially, 3.6 versus 9.8 busy cores; the runner warns that CPU/throughput are not
comparable. This first matched comparison is not a passing performance result.

The initial assigned-base comparison also failed against the historical baseline.
One earlier attempt was invalidated by source edits during run 2 and is excluded.
[ENG-427](https://linear.app/luxdev/issue/ENG-427/mac-studio-bench-baseline-no-longer-reproduces-on-its-own-commit)
tracks that baseline's reproducibility; no tolerances or machine baseline were changed.

The reverse-order repeat measured UF13 first and the accepted integration second,
three runs each under a new shared lease. UF13 versus the first integration result
passed every tolerance. The unchanged integration versus itself flagged two m5
latency metrics; it is not a stable quiet-Host reference. Comparing the repeated
UF13 result with the repeated integration result through the repository's
`compare(...)` function also reports zero regressions.

| Three-run median | Integration first | UF13 first | UF13 repeat | Integration repeat |
| --- | ---: | ---: | ---: | ---: |
| Background busy cores before run | 3.6 | 9.8 | 5.2 | 6.5 |
| m10c3 dispatch-to-event p99, ms | 7.63 | 18.75 | 7.18 | 6.08 |
| m5 dispatch-to-event p99, ms | 6.31 | 7.16 | 4.88 | 11.93 |
| Initial RSS, MiB | 122.44 | 123.00 | 121.55 | 121.45 |

The initial latency flag did not reproduce, and the unchanged integration's own
latency varied. This supports shared-Host variation rather than a demonstrated UF13
regression. It does not establish quiet-Host latency or real-Claude overhead.
No baseline was updated because these loaded-Host measurements cannot replace it.

Raw measurements and the final comparison are committed under
`packages/bench/measurements/eng-657/uf13-{integrated-base,integrated-after,repeat-after,repeat-base,repeat-comparison}.json`.
The sessions scenario uses the scripted benchmark Harness, so it does not measure
real Claude callback overhead. Native correctness evidence above covers the actual
permission and launch path.
