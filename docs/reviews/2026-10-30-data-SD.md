Reviewed: `f172a8a1` (merged in `34c904bf` on the integration branch), diffed against

The Host's load average was 25 to 54 throughout, so treat the timings as rough.

**Verdict.** The decided boundaries hold:

- Remote sources are never snapshotted without an existing approval.
- Postgres `reltuples = -1` stays `unknown`.
- Committing a Turn never waits on a catalog.
- A late capture can't bring back an archived session.
- Nothing runs on a timer.

The Schema Diff itself can't be trusted yet. Three P1s:

- **F1:** cost grows with every Turn, whether or not Data is used. Every Turn start reads the full
  catalog (~3 s here, about 2,000 queries) and stores it. Nothing is pruned, and every read
  decodes the whole session: 200 Turns stored 150 MiB, and one `begin` took 1.7 s.
- **F2:** another session's or the user's changes are attributed to this Turn. Three paths: the
  coalescing cache, staleness keyed by checkout rather than database, and the user's own Data
  activity being ignored.
- **F3:** dropping a table and creating one with the same columns shows as a rename. Rotating a
  partition, which loses its data, reads as a harmless rename.

F4 to F10 are P2s: changes the comparison can't see, including a MySQL index read in the wrong
column order; one wide table hiding every CREATE/DROP; late baselines labelled `turn-start`;
reuse from several Turns back; `prisma db push` hidden; row counts; discovery on every
`bun …` command. F11 to F13 are P3s.

### F1 · P1 · Snapshot cost and storage grow with every Turn, whether or not Data is used

`begin` (`schemaSnapshots.ts:161-173`) runs for every `TurnStarted` in a migration-capable
checkout. For each Local source it calls `beginSource(…, "turn-start", false)`. That saves a row
and, unless it reuses a previous end, captures the full catalog (`:154-158`). Reuse needs a
previous record with an `after` (`schemaStore.ts:64-68`). An unused Turn never gets an `after`
(`schemaSnapshots.ts:206-208`), so in a checkout where the agent never touches Data, every Turn
captures again and stores again.

Nothing deletes these rows except archive and Workspace removal. Every `SchemaStore` read loads
and decodes all of the session's rows, `before` and `after` catalogs included:

- `records(sessionId, turn)` filters the Turn in JS after decoding everything (`:53-60`);
- `previous` decodes everything (`:64-68`);
- `diff` decodes everything even for one Turn (`:92-97`);
- `beginSource` calls `records` and `previous` for each source on every Turn start, Query Log
  touch and outside command.

Probe W7: 200 Turns, one Local source, a realistic catalog (500 tables × 12 columns, one index and
one constraint each), no Data use and no migration change:

| | |
|---|---|
| Rows stored | 200, **150.5 MiB** in `data.sqlite` |
| Catalogs captured | 201 (one per Turn start) |
| `records()` for one Turn | 694 ms |
| `begin()` for Turn 201 | 1,716 ms |
| `get({ sessionId })` | 711 ms, returning 0 sources (none used) |
| The 200-Turn loop | 368 s in total, so per-Turn cost grows with the session's length |

Catalog cost per capture (probe C1, real databases on this Host):

| Engine | Tables | Time | JSON |
|---|---|---|---|
| Postgres | 500 | 3,333 ms | 823 KiB |
| MySQL | 500 | 3,122 ms | 701 KiB |
| Postgres | 5,000 (truncated to 500) | 3,060 ms | 823 KiB |
| MySQL | 5,000 (truncated to 500) | 8,809 ms | 701 KiB |

A capture is one tree query plus four reads per table on Postgres (identity, columns, indexes,
constraints) and three on MySQL. Each read is a full `readEffect` read-only transaction, so 500
tables is about 2,000 transactions. A Pi 4 is several times slower than an M2 Max, which puts a
500-table capture near the 30 s deadline. Then it fails, and is retried on the next Turn.

Suggested fix:

- Take the Turn-start catalog only when the Turn will plausibly need it, or keep it in memory and
  write it only once the Turn is used.
- Delete unused candidate rows at Turn end.
- Store each catalog once, content-addressed, so a reused baseline doesn't duplicate it.
- Query by `(session, turn)` and `(session, source, index)` in SQL instead of decoding the
  session.
- Read the catalog in one query per kind (all columns, all indexes, all constraints for the
  schema), not per table.
- Add a per-session cap or age limit, and a bench scenario.

### F2 · P1 · Changes made by another session, or by the user, are attributed to this Turn

Three separate paths, each probed:

1. **The coalescing cache** (W1). `shared` (`:35`) is keyed by checkout and target, and cleared
   only on Query Log activity or a Turn end (`:176`, `:193`, `:229`). Shell commands and
   migration tools don't clear it.
   - Session A's Turn starts and the catalog has `invoices`.
   - A's agent renames it with `prisma db push`.
   - Session B starts a Turn in the same checkout and gets A's cached catalog as its Turn-start
     baseline.
   - B ends having done nothing. **B's diff: `renamed invoices → bills`, status `complete`,
     baseline `turn-start`.**
2. **Staleness keyed by checkout, not database** (W2). `stale()` counts only activity
   `WHERE checkout = ?`, and `concurrent` only sessions with the same `cwd` (`:119-124`). Polaris
   worktrees of one repository share one compose database, which is the Constellation case.
   - A's Turn 1 ends with a catalog.
   - Session B, in `/model.worktrees/b`, creates `payouts` through Data.
   - A's Turn 2 reuses Turn 1's end: no capture, label `previous-turn-end`. **A's Turn 2 diff:
     `added payouts`.**
3. **The user's own Data activity** (W8). The comment at `schemaStore.ts:69` says un-attributed
   Client writes make a baseline stale. But Desktop queries carry the session's id
   (`queries.ts:55-58`: `{kind: "user", sessionId}`), and `stale()` excludes `session = ?`. The
   user works in the session's Data panel between Turns, and **Turn 2 reports the user's
   `user_scratch` table as the Turn's change**.

The label `previous-turn-end` covers changes outside Polaris between Turns, as decided. It doesn't
cover changes Polaris saw and attributed to someone else.

Suggested fix:

- Key the cache, `stale` and `concurrent` by `targetKey`, not by checkout.
- Clear the cache on any `CommandExecution` and at every Turn start, not only on Data activity.
  Better, drop cross-session coalescing: its only saving is one catalog read.
- Count activity from any author, the same session's user included, as stale.
- When another session worked on the target during the Turn, mark the diff (for example
  `concurrent: true`) instead of presenting it as the Turn's.

### F3 · P1 · Drop + create with the same columns is reported as a rename

`renameMatch` (`schemaCompare.ts:41-44`) treats any same-schema table whose columns are a superset
of the removed table's (by name and type) as its new name. The uniqueness checks
(`:103-107`) stop ambiguous matches but not this one. Probe C3:

| Engine | What happened | Reported |
|---|---|---|
| Postgres | `DROP TABLE audit_2026_09` (one row, analyzed); `CREATE TABLE audit_2026_10 PARTITION OF audit …` | `renamed audit_2026_09 → audit_2026_10`, no column changes, rows `unknown` |
| MySQL | `DROP TABLE audit_2025`; `CREATE TABLE audit_2026 (… same columns …, note text)` | `renamed audit_2025 → audit_2026`, column `note` added, rows `estimate −1` |

The reviewer sees a rename, which keeps rows, when the data was dropped. The other rename cases
held (probe C4): two renames at once (`a → a2`, `b → b2`) were detected, and a rename plus a column
rename (`c → c2`, `z → zz`) fell back to removed and added, which is conservative.

Suggested fix: use the engine's stable identity and stop guessing from columns. A Postgres rename
keeps `pg_class.oid` and a drop/create doesn't; MySQL's
`information_schema.INNODB_TABLES.TABLE_ID` survives `RENAME TABLE`. Capture it in the snapshot
(it isn't on the wire) and pair by it. Keep the column heuristic only where no id exists, and say
"possibly renamed" there.

### F4 · P2 · Changes the comparison can't see

Probe C5 applied these changes. **Both diffs were empty**:

| Engine | Change | Why it's missed |
|---|---|---|
| MySQL | index `ab (a, b)` → `ab (b, a)` | `JSON_ARRAYAGG` without `ORDER BY SEQ_IN_INDEX` (`catalog.ts:56-58`): **the new index reads `["a","b"]`**, the wrong order |
| MySQL | index `nm (name)` → `nm (name(4))` | `SUB_PART` isn't read; `definition` is only `MIN(INDEX_TYPE)` = `BTREE` |
| MySQL | generated column `a * 2` → `a * 3` | `GENERATION_EXPRESSION` and `EXTRA` aren't read |
| MySQL | collation `utf8mb4_bin` → `utf8mb4_general_ci` | `COLUMN_TYPE` omits the collation |
| MySQL | `ON UPDATE CURRENT_TIMESTAMP` added | `EXTRA` isn't read |
| Postgres | collation `"C"` → `"en_US.utf8"` | `format_type` omits the collation |
| Both | `CREATE OR REPLACE VIEW` with a new column | views are skipped (`schemaCatalog.ts:25` iterates `group.tables` only) |
| Postgres | a trigger added, RLS enabled, a column comment | not captured |

Postgres reports the generated column `g` as `default: "(a * 2)"` (`pg_get_expr` on `adbin`
without `attgenerated`).

The MySQL index-order bug also misreports the live Data catalog, which shares `indexesSql`.

Suggested fix:

- `JSON_ARRAYAGG(… ORDER BY SEQ_IN_INDEX)` isn't allowed, so aggregate from a sorted derived
  table, or build the array in JS. Include `SUB_PART` and `COLLATION` (sort direction).
- Read `GENERATION_EXPRESSION`/`EXTRA`, `COLLATION_NAME` and Postgres `attgenerated`/`attcollation`.
- Add views (their definition hash), triggers and RLS as object kinds.
- Label in the UI what the diff doesn't cover.

### F5 · P2 · One wide table hides every table addition and removal

`snapshotCatalog` sets `truncated` when any table has ≥ 256 columns, indexes or constraints
(`schemaCatalog.ts:41-45`). `compareCatalogs` then treats the whole catalog as partial: no
renames, no additions, no removals, only changes to matched tables (`schemaCompare.ts:96-121`).

Probe C2, on both engines: an `events_wide` table with 301 columns. `DROP TABLE legacy` plus
`CREATE TABLE payouts` gives **an empty diff**, with `truncated: true`. The UI can only say "may
be incomplete" for a whole schema because of one analytics table.

`>= 256` also flags a table with exactly 256 columns, which wasn't truncated.

Suggested fix: carry two flags, "the table list is incomplete" and a per-table "details
incomplete". Only the first should stop additions and removals. Detect detail truncation with
`limit + 1` (257), not `>= 256`.

### F6 · P2 · Late baselines are labelled `turn-start`

All signals go through one `Stream.runForEach` (`schemaSnapshots.ts:263-298`). A capture can take
up to 30 s per source, so a `TurnStarted` queued behind another checkout's capture is handled
after the Turn is already running.

Probe W5: B's catalog blocks the worker. A's `TurnStarted` is committed at `01:34:46.261`, and A's
agent renames `invoices` right away. A's baseline is taken at `.373` and still labelled
`turn-start`. **A's diff is empty.** The same delay applies to `TurnEnded`. The end catalog of
Turn N can include Turn N+1's first statements, and with reuse those then appear in N, not N+1.

First-use has the same race: `log.touch(entry)` runs just before `readEffect`
(`queries.ts:101`), and outside commands are seen at their first progress item. Both trigger the
baseline capture in parallel with the statement, never before it. For a Remote source, a W write
or a `psql` DDL on first use can land before its own baseline, leaving a `complete` diff with
nothing in it.

Suggested fix:

- Stamp the label from timing: record `TurnStarted.at` and mark the baseline `late` when it's
  taken after it.
- Run captures per target in parallel with a small cap, keeping the serial order within one
  target.
- For first-use on agent writes (W), take the baseline inside the write path, before the
  statement. This doesn't touch decide or ack, because writes already wait for approval.

### F7 · P2 · `previous-turn-end` reuses an end from several Turns back

The decision is that the baseline reuses the previous Turn's end. `previous`
(`schemaStore.ts:64-68`) instead returns the latest earlier record with an `after`, from any
earlier Turn.

Probe W3:

1. Turn 1 used the source; its end has `invoices`.
2. Turn 2 reused it (`previous-turn-end`) and dropped `invoices` through
   `docker compose exec db psql`. That's unmatched, so Turn 2 wasn't used and got no end catalog.
3. Turn 3 only added a migration file and reused Turn 1's end. **Turn 3's diff: `removed
   invoices`.** Turn 2's diff is empty.

Suggested fix: reuse only when `previous.index === turn.index - 1`. Otherwise capture, or label
the baseline with the Turn it came from.

### F8 · P2 · Schema changes without Data or a migration file are hidden

At Turn end a row is kept only if Data was used, a migration path changed in the checkpoint
diff, or a Query Log entry names the source (`schemaSnapshots.ts:206-208`). The common ways an
agent changes a local schema without either: `prisma db push`, `drizzle-kit push`,
`supabase db reset`, re-applying committed migrations after a pull, `docker compose exec db psql`
(`outsideMatches` only matches direct `psql`/`mysql` or `bun -e`).

Probe W4: the Turn-start catalog was captured and stored, the agent added `payouts`, and **Review
shows no source**.

Suggested fix: the baseline is already paid for (F1). At Turn end, compare the tree query alone
(one query: table names, column names and types) with it, and take the full end catalog only when
they differ.

### F9 · P2 · Row counts

- **Estimates don't move** (probe C6). On both engines, `+4,900` rows written outside Polaris left
  the estimate at `100 → 100`. Postgres `reltuples` waits for autovacuum or ANALYZE; MySQL caches
  `TABLE_ROWS` for `information_schema_stats_expiry = 86400` s. A zero estimate delta drops the
  table from the diff (`schemaCompare.ts:129-139`), so "rows changed" and "estimate stale" look
  identical. Keep the table with `estimate 0` when the Turn ran unmatched commands, or label
  estimates "may lag".
- **`exact` when only part of it is known** (by reading, `schemaCompare.ts:51-63`). One counted
  write to a table makes the whole row card `exact`. Writes from `psql`, migrations or other
  outside paths aren't added. An agent that updates 5 rows through W and runs `psql -c 'DELETE
  FROM t'` sees `exact 5`. Mark it `exact` only when no unmatched outside command or migration
  touched the source in the Turn; otherwise use `at least`.
- **Held:** `failed` and `cancelled` entries are excluded (`state === "completed"`, `:166`).
  Postgres `reltuples = -1` gives `unknown` (C6: new table `fresh` → `unknown`). A new MySQL table
  reports `TABLE_ROWS = 0`, which becomes `estimate 0`, not unknown.
- **User counts per Turn** (by reading). A user `data.edits.commit` between Turns has no `turn`
  (`queries.ts:55-58`), so it's never in a per-Turn card, only in the whole-session diff.
- **For W's producer** (probe C8, Bun SQL on MySQL 8.4): `UPDATE … SET v = 1` on a row already 1
  gives `affectedRows 0`; an `INSERT … ON DUPLICATE KEY UPDATE` that updates one row gives `2`;
  `REPLACE` of one row gives `2`. Postgres gives `1` for both. W must count rows matched
  (`CLIENT_FOUND_ROWS`) or say which semantics it uses, or MySQL cards will be doubled or zero.
  Rolled-back writes are W's to guarantee: `completed` must mean committed.

### F10 · P2 · Source discovery on every `bun …` command

`outside` (`schemaSnapshots.ts:232-251`) runs for every `ItemProgress` of a `CommandExecution`,
in every session, whose text matches `\b(psql|mysql|pg_dump|mysqldump|bun|node)\b`. It ignores
whether the checkout is migration-capable or the session uses Data. It calls `sources.list`, and
then `sources.resolve` once per source. Each call is a full `catalog(sessionId)`: discovery
(reading `.env` and compose files, up to 2 s), an `lsof` per candidate (macOS) and an approval
read. `resolve` builds a fresh `localityProbe`, so nothing is cached.

Probe W6: three progress items of `bun test apps/daemon`, with one source and Data unused, gave
3 `list` and 3 `resolve` calls, so 6 discoveries.

Separately, `ItemProgress` is ephemeral: `LiveHub` drops it once the worker's queue is half full
(`store/hub.ts:148-151`). While a capture runs, outside-command signals can be lost.

Suggested fix: match the command text against the resolved sources' URLs and keys once, using
the sources from the Turn's start (cache them per Turn). Skip non-client commands before any I/O.

### F11 · P3 · Secrets in catalog text are persisted per Turn

Probe C7: a column `DEFAULT 'sk_live_…DEFAULT'`, a `CHECK (token <> 'sk_live_…CHECK')` and (on
Postgres) a partial index `WHERE token = 'sk_live_…INDEX'` all appear verbatim in the snapshot
JSON. That JSON is stored in `data.sqlite` once per Turn (F1) and served by `data.schemaDiff`.
Function bodies and view definitions aren't captured.

The live catalog already shows the same text, so this is a persistence and retention issue, not a
new exposure: a rotated secret survives in old snapshots until the session is archived. Suggested
fix: pass defaults, check definitions and index predicates through the Query Log's literal
redaction, or store a hash and show the text only from a live read.

### F12 · P3 · Every capture failure becomes `E-DATA-TIMEOUT`

`Effect.mapError` after `Effect.timeout` (`schemaSnapshots.ts:60-70`) replaces every error,
including `E-DATA-DENIED`, auth and missing-table errors, with "could not be completed". The
record keeps only `failed: true`, so Review can't say why a source is `unavailable`. Map only the
timeout, and store the error's code on the record.

### F13 · P3 · README accuracy

`apps/daemon/src/data/README.md` (Schema Diff) says:

- "Source discovery only runs on Turn boundaries or Data activity". It also runs on every
  matching command's progress (F10).
- "adjacent starts coalesce until Data activity". The cache is shared across sessions and survives
  shell commands (F2).
- "no other session has since used the checkout's Data". The hazard is the database, not the
  checkout (F2).
- "A previous Turn's end is reused". It's any earlier Turn's end (F7).

`packages/spec/README.md`'s note is accurate: the worker adds no decide, ack or commit transition,
and `bun run spec` passes. None of F2, F6 or F7 is a Session-machine property, so the spec isn't
the place to catch them. A model-based test of the worker over interleaved sessions, Turns,
activity and catalog changes would be.

## Checked and holding

- **Remote sources.** `snapshotAllowed` (`schemaCatalog.ts:11-13`) needs Local, or Remote with
  `approved`. `begin` skips Remote sources (`:115`, `:171`). `end` re-resolves and marks the row
  failed when the target or locality changed (`:209-213`), so a Local source that becomes an SSH
  tunnel to production by the end of the Turn isn't read. The snapshot path never calls
  `approvals.require`. RX F1's Remote `access: read` doesn't pass `snapshotAllowed`. SD's test
  "remote baseline never reads or asks" passes.
- **Commit independence and cleanup.** `TurnEnded` commits while a catalog is blocked, archive and
  Workspace removal delete records, and a late save after archive is discarded (`save`, `:43-48`).
  SD's tests pass.
- **Idle.** No timer, `Schedule` or sleep in `schemaSnapshots.ts`, `schemaStore.ts`,
  `schemaCatalog.ts`, `schemaMigrations.ts` or `schemaCompare.ts` (grep). The snapshot `DataPools`
  is lazy, with Bun's one-shot 5 s idle close.
- **Two renames at once, and rename plus alter** (C4), as in F3.

Runs (all exit 0 unless noted):

- `bun test` on SD's nine focused files: 65 pass, 0 fail, 178 assertions.
- `POLARIS_TEST_PG_URL=… POLARIS_TEST_MYSQL_URL=… bun test
  apps/daemon/src/data/schemaSnapshots.real.test.ts`: **2 pass, 0 fail**. This is the native
  Postgres rerun after SD's ANALYZE fix, which SD's Claim listed as not done.
- `bun run spec`: all scenarios and simulations pass, and the expected finding mutants still
  violate.
- Probes: `rsd.worker.probe.test.ts` W1 to W8 reproduce. W7 overruns the 120 s test timeout it
  ran with (368 s), which is itself the F1 result; the shipped copy allows 900 s. All of
  `rsd.catalog.probe.test.ts` C1 to C8 ran, and the `rsd_sd_probe` databases were dropped
  (checked afterwards).
