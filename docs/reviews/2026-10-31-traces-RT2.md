## Findings

### F6. P0: SLOW span history locks the trace worker (CONFIRMED)

`apps/daemon/src/traces/queries.ts:213` (`JOIN spans c ON c.checkout=? AND json_extract(c.value,'$.name')=w.name`);
`queries.ts:192` (second `getTrace` of the same trace); called from `apps/daemon/src/mcp/tools/traces.ts:198`.

`EXPLAIN QUERY PLAN` shows `SCAN w` → `SEARCH c USING INDEX sqlite_autoindex_spans_1 (checkout=?)`.
For every distinct (name, parent name) pair in the trace, SQLite walks every Span in the checkout
and parses its JSON `value`, then parses the parent's JSON too. The work grows as pairs × stored
Spans. It runs on the single trace worker, so every other trace RPC waits behind it: the Desktop's
Traces list, `get`, `watch` pages, other agents' tools and the ingest flush. A concurrent
`store.list` waited 6.5 s on a 5k-Span store. With 105k stored Spans (well under the 200 MiB
retention) one `trace` call did not finish in 10 minutes. That is a hang for every trace consumer
on the Host, and exporters back up into the receiver's queue while it lasts.

Repro: `performance.test.ts` › F6 (asserts under 2 s and a concurrent list under 250 ms).

Smallest fix: at ingest, store `name` and `parent_name` as columns (fill `parent_name` when the
parent arrives, or resolve it in `refreshSummary`). Index `spans(checkout,name,parent_name)`, join
on those columns, and bound the samples to the most recent K earlier traces per pair (for example
K = 50). Pass the already-loaded Spans to `traceHistory` instead of calling `getTrace` again.

### F1. P1: focus slow renders in keep order, not tree order (CONFIRMED)

`apps/daemon/src/mcp/tools/traceFormat.ts:338` (lines are pushed in `orderedGroups`' priority
order), `traceFormat.ts:266`.

The cap priority (error paths, then the critical path, then the rest by duration) is also used as
the display order. Take R → {X → {E (error), C}, B → B1}. The output is `R, X, E, B, B1, C`. C
appears at depth 2 straight after B1, so an agent reading the indentation takes C as B's child. The
spec's own example is in tree order and describes the priority as the "order of keeping under the
cap".

Repro: `summariser.test.ts` › F1 (parses the text the way an agent would; C's parent reads as `B`).

Smallest fix: choose the kept groups by priority as now, then render the kept set by a DFS from
the roots in start order. Error and critical members keep their markers.

### F2. P1: deep error paths lose the error itself (CONFIRMED)

`traceFormat.ts:225` (indent `"  ".repeat(depth)`), `traceFormat.ts:270–283` (the whole ancestor
chain is queued), `traceFormat.ts:351`.

Each line costs 2 × depth characters of indentation, so a root-to-error chain costs about d²
characters. With an error at depth 149, even `focus: "errors"` prints about 120 ancestors and then
runs out of room. Neither the ERROR line nor the exception appears; the header still says
`1 errors`. Recursive code (parsers, ORMs, middleware stacks) produces exactly these traces. A
1,000-deep chain gives 15,816 characters, 891 Spans folded, and only about 110 levels shown.

Repro: `summariser.test.ts` › F2.

Smallest fix: reserve the error line and its exception before its ancestors. Elide the middle of
long paths (`… 130 levels …`, keeping the root, the last 5 ancestors and the error). Cap visual
indentation at about 20 levels and write the real depth as `[depth 149]`.

### F3. P1: one huge row empties `traces` (CONFIRMED)

`apps/daemon/src/mcp/tools/traces.ts:94–110`.

Rows are built from `root`, `service` and the first error message with `inline` only, never
clipped; the decoder has no attribute or name length limit. The cap loop then drops rows from the
end until the text fits. If the newest row is too long by itself, the count falls to 0 and the
tool prints `All turns · 2 traces (0 shown of 2; add limit or narrow filters)`. A 20,000-character
exception message hid both traces. A 200,000-character root name did the same (probe). Neither
limit nor a narrower filter helps.

Repro: `summariser.test.ts` › F3.

Smallest fix: clip each row's root, service and error message (for example to 200 characters with
`…(+n chars)`, the Data tools' value rule) before the cap loop. Keep the full values in
`structuredContent`.

### F4. P2: `trace` on large traces is slow and blocks the main thread (CONFIRMED, measured)

`apps/daemon/src/traces/store.ts:73–89` (the full `TraceDetail` is re-decoded with Effect Schema
on the main thread), `apps/daemon/src/mcp/tools/traces.ts:192–199`, `traceFormat.ts:324`
(summarised on the main thread).

A 50k-Span trace took 3.1 s and stalled the Daemon's event loop for 567 ms. That stall covers
every RPC, Agent Session streams and the Desktop. A 10k-Span trace: 540 ms, 105 ms stall.
Separately, 10k identical zero-length siblings took 5.6 s (probe; it includes that trace's history
query, see F6).

Repro: `performance.test.ts` › F4.

Smallest fix: add a `Summary {checkout, traceId, focus}` worker request that runs `traceView` and
the history lookup next to the data and returns only `{text, data}`. The main thread then decodes
at most the displayed Spans.

### F7. P2: `traces` loads full error traces (CONFIRMED, measured)

`apps/daemon/src/mcp/sessions/traces.ts:70–79`.

For every error trace on the page, `list` calls `store.get`, which loads and decodes every Span, to
find one message. 20 error traces of 5k Spans took 21 s; a 50-trace page is proportionally worse.
T2's claim says listing "avoids loading Span details", but that only holds for history.

Repro: `performance.test.ts` › F7.

Smallest fix: one worker query per page. Select the first error Span's `exception.message` or
`statusMessage` by `(checkout, trace_id) IN page AND status='error' ORDER BY start LIMIT 1` per
trace, or keep it in `summaries` from `refreshSummary`.

### F8. P2: `span` loads the whole trace (CONFIRMED, measured)

`apps/daemon/src/mcp/tools/traces.ts:211`.

`traces.get(checkout, input.trace)` loads the full trace only to read
`summary.startTimeUnixNano` for the offset. On a 50k-Span trace `span` took 8 s, against 47 ms for
`store.span` alone.

Repro: `performance.test.ts` › F8.

Smallest fix: return the trace start in `SpanDetail` (or use a summary-only read).

### F5. P2: identical failing siblings are never collapsed (CONFIRMED)

`traceFormat.ts:143–146` (the group key for error Spans is the Span id).

300 `GET /rates` children that all failed with `connect ECONNREFUSED` give 300 two-line blocks. The
cap fills with them, and the 600 ms `UPDATE invoices` critical path is folded. This follows the
spec ("Error paths remain individual when their error Spans share a name"), but the result is the
434-line page the spec is meant to prevent. Retry storms and N+1 loops against a dead dependency
produce it.

Repro: `summariser.test.ts` › F5.

Smallest fix (spec change): collapse error siblings with the same name, parent, exception type and
message into `×300 GET /rates ERROR  p50 …` with one exception sample. Keep every id in
`structuredContent`, and reserve room for the critical path after at most N error lines.

### F10. P2: group SLOW uses the first member (CONFIRMED)

`traceFormat.ts:226–231` (`history.spans[first.id]` compared with `first.durationMs`).

A group of 30 `GET /rates` (p50 2 ms) whose first member happened to take 60 ms prints
`×30 GET /rates  p50 2 ms  total 118 ms  SLOW (usually 2 ms)`. The opposite case: a group whose
first member is normal is never SLOW, however slow the rest are. The spec defines SLOW per Span; for
a group it is unspecified.

Repro: `summariser.test.ts` › F10.

Smallest fix: compare the group's p50 with the usual value, and say so in the spec.

### F11. P2: `span` cap drops whole lines first come, first served (CONFIRMED)

`traceFormat.ts:89–116` (`capSections`), `spanFormat.ts:74–127` (attributes come before events and
logs).

A 14,000-character `db.query.text` (ORMs routinely generate `IN (…)` lists that long) fits the
budget, and then every event, exception stack line, log and link is omitted. The exception that
made the agent call `span` is gone from the text. A line just over the budget is dropped whole
rather than clipped.

Repro: `span.test.ts` › F11.

Smallest fix: clip each line to about 2,000 characters with `…(+n chars)`. Emit sections by value
(header, code, exception and in-project frames, logs, then attributes, resource and scope), or give
each section a budget.

### F14. P2: lone surrogates and bidi controls reach the text (PLAUSIBLE)

`traceFormat.ts:7–10` (`inline` strips only C0 and DEL).

A probe with the span name `"‮evil\u0000\uD800…"` produced text containing U+202E and an
unpaired `\ud800`. OTLP/JSON allows such escapes and the decoder keeps them. `JSON.stringify` writes
a lone surrogate as `\ud800`, which `serde_json` (Codex's MCP client) rejects as an invalid escape,
so one bad name could fail the whole tool result on the Codex binding. Bidi overrides can make a
name read differently from its bytes. I did not run a Codex session, so this is PLAUSIBLE.

Smallest fix: `inline` applies `String.prototype.toWellFormed()` and replaces U+202A–U+202E and
U+2066–U+2069 with spaces. Better still, the decoder does this once at ingest (T1's area).

### F12. P3: printed 8-hex Span prefixes aren't unique (CONFIRMED)

`traceFormat.ts:236` (`span.id.slice(0, 8)`).

Span ids are 16 hex characters, and 8-hex prefixes collide by the birthday bound: about 1% of
10k-Span traces and about 25% of 50k-Span traces have at least one collision. Following the
printed prefix then gets `E-TRACE-AMBIGUOUS`. The same holds for `traces` rows' 8-hex trace ids in
a large checkout.

Repro: `span.test.ts` › F12 (two Spans sharing `abcdef01`).

Smallest fix: print the shortest prefix of at least 8 characters that is unique within the trace
(and within the page for `traces`).

### F13. P3: E-INPUT doesn't say what's wrong (CONFIRMED)

`apps/daemon/src/mcp/tools/traces.ts:146–151`.

`trace {id: "1234567890ABCDEF…"}` (uppercase, as some UIs and logs print ids) returns
`Use the fields in this tool's input schema.`. The agent can't tell that case is the problem.

Repro: `span.test.ts` › F13.

Smallest fix: include the Schema issue path and message, or a per-tool fix:
`ids are 8–32 lowercase hex characters`. Alternatively, lowercase ids before decoding.

### F15. P3: `focus: "errors"` with no errors (CONFIRMED by probe)

`traceFormat.ts:285–287`.

On a trace with 0 errors the text is the header plus `… 5 spans under 11 ms folded; use span for
details.`, which reads as if something was cut. Smallest fix: print
`No error spans; use focus slow.`.

## Attacked, no finding

- **Bindings.** Every binding comes from one `attachSessionTools` in `mcp/http.ts`, which the HTTP,
  Claude in-process and Codex transports share. T2's catalog test calls each tool on every binding.
  All three are `readOnlyHint`. Excess properties (`sessionId`) give E-INPUT.
- **Cross-session and cross-checkout.** The checkout always comes from
  `TraceSessions.session(callerId)`. Every query filters `checkout=?`. Explicit Turn numbers resolve
  only in the caller's session, and an unknown number gives E-TRACE-NOT-FOUND. A trace from another
  checkout is not listed (T2's test). Prefix `LIKE` takes only `[0-9a-f]`, so it can't inject
  wildcards.
- **Turn current, all and number with no active Turn.** `current` falls back to `turn_id IS NULL`,
  labelled `Between turns`; `all` spans the checkout; numbers come from the caller's session. This
  matches the spec. TurnIds are UUIDs, so `turn_id IS ?` can't match another session's Turn.
- **SLOW sample rules.** The root and Span medians need `count>=5`, use strictly earlier `start`
  and exclude the trace itself (`trace_id<>?`); the median is correct for even counts. The 20 ms
  and 3× rule is enforced in both tools. Only cost is a problem (F6).
- **Adversarial shapes (probes).** A parent cycle (A↔B), a self-parent, a missing root, an orphan
  and a duplicate Span id (stored as last-write-wins) all render with every Span accounted for,
  with no crash or hang. 10k identical siblings collapse to `×9999 … (N+1?)`. Zero-length Spans
  print `0 ms`. Depth 1,000 stays under 16,000 characters (15,816). ESC and NUL are stripped. A
  negative offset can't occur because the decoder rejects end < start, and offsets are measured
  from the trace's earliest Span.
- **`Math.max(...spread)`** on folded Spans: Bun handles 500k arguments and fails only near 1M,
  beyond what one trace can hold under retention.
- **The 16,000-character cap.** No output exceeded it in any repro or probe; errors are sliced to
  it.
- **`span` details.** The 20-log cap and the "older logs omitted" count are correct. A null
  launched Turn prints no line. Redacted values come from storage (T1's redaction; see RT1 F1 and
  F2 for its gaps).
- **Data Source matching.** It needs engine, host and database, normalises loopback names, and
  defaults the port by engine. It returns a source only when exactly one matches, so two sources on
  the same server and database (different users) give none, and a remote source matches only its
  exact host. The Data tools still enforce Remote Data Source approval on `describe` and `query`.
- **E-TRACE-NONE and E-TRACE-UNAVAILABLE.** They follow the spec. The NONE fix includes the session
  endpoint with its token, as the spec requires. The token is already in the agent's environment,
  so this is noted only.
